# Aoysky Selection · 红人专属选款网站

用来替代 Google Sheet 选款表的轻量站点。红人按栏目浏览、挑颜色和尺码、按件勾选，生成专属选款码；运营粘贴代码即可还原全部明细，导出 CSV 或 JSON。

界面全英文，面向英文环境的红人与买手团队。

- **多人实时协作**：数据在 Supabase Postgres，两个人同时改商品库，另一头几秒内自动刷新
- **栏目导航**：按分类筛选，分类可自己增删改名
- **搜索 + 分批加载**：按货号或名称搜索，首屏 24 个，点 Load more 再加一批；分页永远在"当前分类 + 当前搜索词"的结果里翻
- **同款可多选**：按「商品 + 颜色 + 尺码」加购，同款选 Black/M 还能再选 White/L，底部栏分款式 / 变体 / 件数三层计数
- **购物袋预览**：随时查看已选款式、颜色尺码、数量，可直接改，也可以一键清空（先确认）
- **颜色和尺码必须显式选择**，不预填默认值
- **选款码自包含**：红人手机生成，运营电脑解码，不依赖服务器
- **一键跳亚马逊**：卡片和详情弹层都有 `View on Amazon ↗`，方便看尺码表和评价
- **内置商品编辑器**：URL 填图、颜色/尺码可视化编辑、分类下拉、上架开关、批量下架，无需改代码
- **开发者可直接取数**：浏览器控制台、CLI、JSON 三条通道
- **后台是真登录**：Supabase Auth 邮箱+密码，不是前端口令；ASIN 清单匿名读不到，打包产物里也没有任何 ASIN

## 一、页面与路由

| 路由 | 页面 | 说明 |
|---|---|---|
| `/#/` | 选款页 | 红人使用 |
| `/#/?ref=luna` | 选款页（带身份） | `ref` 显示在右上角并写入选款码 |
| `/#/admin` | 后台 · Lookup | 粘贴选款码查询 · **需要登录** |
| `/#/admin/products` | 后台 · Products | 商品库编辑器 · **需要登录** |
| `/#/admin/developer` | 后台 · Developer | 选款码转 JSON · **需要登录** |

后台三个页签都不在前台放显眼的入口，而且整个 `/#/admin…` 前缀都走登录门禁（见第十四节）：邮箱 + 密码，走 Supabase Auth，账号必须在 `admin_users` 白名单里。运营自己的入口只有两处：页脚一行很淡的 `Admin Login`，以及在选款页直接敲 `admin`。使用 HashRouter，静态托管刷新不会 404，无需 rewrite 配置。

**发链接给红人的正确姿势**（每人一个专属链接，`ref` 只用字母数字，最长 12 位）：

```
https://your-domain.com/#/?ref=luna
https://your-domain.com/#/?ref=chenxi01
```

### 品牌文案在哪改

页眉的品牌名、logo 字母、欢迎语、副标题，以及页脚那句使命，全部来自 `src/data/products.js`
里的 `brandConfig`：

```js
export const brandConfig = {
  name: 'Aoysky',
  welcome: 'Move Free, Feel Premium',
  tagline:
    'Blends activewear with everyday style, moving effortlessly from workouts to real life.',
  mission: "Make activewear seamlessly part of every woman's daily life.",
  logoText: 'A',
}
```

> **改这里的同时改 `scripts/build-catalog.mjs` 顶部的 `BRAND_CONFIG`。**
> `npm run catalog` 会用生成器重写 `src/data/products.js`，只改生成结果的话，下一次
> 导入商品表就会把文案换回去 —— 两个地方必须一起改。

四级字号/灰度的分工是有意的：

| 位置 | 字段 | 呈现 |
|---|---|---|
| 页眉大门票 | `welcome` | 26→36px 半粗（`text-[26px] font-semibold sm:text-4xl`） |
| 页眉副标题 | `tagline` | 14→15px 常规灰 |
| 页脚使命 | `mission` | 11px，最轻的一档灰度（`text-charcoal-light/50`） |
| 页脚配货声明 | 硬编码 | 11px，稍重（`text-charcoal-light/60`） |

使命排在配货声明**之上**：一句品牌宣告不该落在流程条款后面。它又是全页最淡的一句 ——
读到这里的人已经在浏览了，不需要再被推销一次。

`index.html` 的 `<title>` 和 `<meta name="description">` 是**另外两处**，不在 `brandConfig` 里，改品牌名要一起改。后台登录墙（`AccessGate`）和查码页的提示文案里也各有一处品牌名。

**标签页图标**在 `public/favicon.svg`，是第四个地方：`brandConfig` 换成 `Aoysky` 之后图标还写着 `M`，一眼就能看出来。

- 字母是**描边路径**画的，不是 `<text>`。favicon 在自己的文档里渲染，拿不到页面的 webfont，`<text font-family="Inter">` 会回退到系统字体 —— 每个平台形状都不一样，而标签页上只有 16px，那就是整个图标。
- 引用带 `?v=2`：浏览器对 favicon 的缓存比任何资源都顽固，改完不换 URL 会继续显示旧图标好几天。**换图时必须把版本号加一。**
- `npm run smoke` 的 `[1b] Brand` 会真的 `fetch` 这个文件，断言它用的是品牌色 `#C8855A`、且**不含 `<text>`**（检查前先剥掉 XML 注释，否则注释里提到 `<text>` 会误报）。

`npm run smoke` 的 `[1b] Brand` 会读渲染后的 `document.title`、页眉和整页正文，断言出现 `Aoysky`、且**任何位置都不出现 `MAKO`** —— 漏改一个字符串在代码评审里看不出来，在页面上很显眼。

### 后台查码结果页的四个动作

粘贴选款码 → 明细出来后，底部是四件事：

| 动作 | 产出 | 给谁用 |
|---|---|---|
| `Export CSV` | 一行一个变体，含货号 / ASIN / 规格 / 数量 / 状态 | 存档、发给仓库 |
| `Copy list` | 带表头的纯文本，含选款码和生成时间 | 粘贴进微信 / Slack 回人 |
| `Copy All ASINs` | **一行一个裸 ASIN，别的一律没有** | 粘进亚马逊后台或 ERP 的批量框 |
| `Open in Developer` | 跳 `/#/admin/developer`，把码转成 JSON | 接系统 |

`Copy All ASINs` 的规则（每一条都有测试盯着）：

- 只输出 `item.asin`，**不带引号、逗号、序号、货号、商品名、数量**
- 一行一个，**没有结尾换行**，也没有空行
- `No matching ASIN` 的行**直接跳过**，不留空行
- 按选款码里的顺序，重复的 ASIN 只出现一次
- 整个选择里一个 ASIN 都没有时，按钮变成 `No ASINs to copy` 并置灰，不会复制出一个空字符串
- 成功后 Toast 显示 `N ASINs copied to clipboard`

> 数量不进这个清单是有意的：这个按钮的用途是"这次要下哪些 listing"，件数看表格或 CSV。真需要按件下单时用 CSV。

## 二、红人选款流程

1. **找款**：顶部吸顶栏是搜索框 + 分类 chip。可以只按分类翻，也可以直接搜货号或名称，两者**同时生效**
2. **往下翻**：首屏 24 个，点 **Load more** 再加 24 个。按钮下方写着 `Showing 24 of 139`，全部加载完后变成 `That's all 139 styles` 并且按钮消失
3. **选颜色和尺码**：点卡片 → 详情弹层，**颜色和尺码都选完**，底部按钮才可点。断货的选项是灰的、带删除线、写着 `(Sold out)`，点不动
4. **调数量**：加入后卡片上出现 `− 1 +` 步进器
5. **同款换色再选一份**：想给同一款再要一个颜色/尺码，重新点卡片选另一个组合加购即可。卡片按钮变成 **Manage (2)**，点开弹层会列出这款已经选过的所有组合，可单独减或删
6. **看购物袋**：点底部栏左侧计数，抽屉里能看到每一行的颜色、尺码、数量，可直接加减或移除，点某一行可回去改规格
7. **反悔**：抽屉底部 `Clear all` → 就地确认 → 整个选择归零
8. **生成码**：抽屉里或底部栏点「Generate my code」，复制发给对接人。**购物车不会被清空**——7 天有效期会重置，红人继续加购后再生成，新码包含全部已选款式

> **选完之后才断货怎么办**：抽屉里那一行会变红并标 `Sold out`，`Edit` 换成 `Remove`，底部出现 `Remove sold-out items` 一键清掉，`Generate my code` 在有断货行时是灰的。**不自动删** —— 悄悄删掉会让红人以为自己点错了，她可能只是想换个尺码。

底部栏计数分三层：`3 styles · 5 variants · 7 items` —— 款式（不同商品数）/ 变体（不同颜色尺码组合数）/ 件数。只有一个变体时中间那段省略。

> 颜色和尺码**不做默认预选**。默认值对红人是隐形的，等运营收到错款才发现，返工成本高。宁可多一步点击。
>
> 列表页卡片图**永远**是商品的主图，切颜色不会换图 —— 换图只发生在详情弹层里。列表页是"认款"的地方，图一动红人就找不到自己刚看的是哪一件了。
>
> **卡片和弹层统一：正方形画框（`aspect-square`）+ 纯白底 + `object-contain` + 无边框 —— 抄亚马逊主图。**
>
> 这个位置改了六轮，每一轮的结论都写在这里，因为下一次一定会有人想再改：
>
> | 方案 | 结果 |
> |---|---|
> | `aspect-[4/3]` + `cover` + 米白底 | 3:4 竖图被横着裁掉 40%，"怼脸" |
> | 定高画框 + `contain` + 米白底（弹层） | 弹层对了 |
> | `4:5` + `contain` + 米白底（卡片） | 长裤缩成中间一条，两侧各 30% **米白色带** —— 留白比裁切更难看 |
> | `3:4` + `cover` + 米白底 | 网格齐了，但细长图上下裁掉 42% |
> | `3:4` + `contain` + 纯白底 | 留白隐形了，但**同一行商品视觉大小严重不一致** |
> | `aspect-square` + `cover` + `object-top` + `#F8F8F8` | 阵列齐、无留白、保住腰头；但商品被裁 |
> | **`aspect-square` + `contain` + 纯白 + 无边框**（现在） | **完整不裁；留白与白棚背景同色所以看不见；网格仍是正方形，行列绝对齐** |
>
> 三个结论，都不显然：
>
> 1. **底色比 fit 更能决定观感。** 同样一条 60px 的带子，在 `cream-dark`（#F2EEE8）上读作"图片被截断了"，在白上直接消失 —— 因为商品图本来就是白棚拍的。
> 2. **`contain` 的白边能不能"看不见"，取决于底色是否和原图背景同色。** 这是本轮换回 contain 的前提：底色必须是**纯白**，不能是近白（`#F8F8F8` 也不行），否则白边会显形成一块面板。
> 3. **但"白边隐形"不等于"商品一样大"。** 源图宽高比从 0.43（长裤）到 0.99（半裙），`contain` 下长裤在 260px 画框里只占 112px 宽，视觉上就是比内衣小一半。**这是 contain 的固有代价，亚马逊能接受是因为它的商品图统一拍摄比例。** 要真正解决，得在**源图**上把商品裁成统一占位（见第五节），CSS 做不到。
>
> 没有边框，也不该有：灰色 hairline 会把隐形的留白勾成一块看得见的面板，商品立刻显得小。页面底色是 `bg-cream`，白卡片自己就有边界。`smoke-live` 把卡片 `borderTopWidth` 断言成 `0px`，就是防这条灰边被加回来。
>
> `aspect-*` 必须写在**画框**上，不能写在 `<img>` 上 —— 网格列等宽，一个比例就是一个高度；写在图上则每张图按自身比例撑高，行就散了。`smoke-live` 的 `[2b]` 断言所有卡片图片框的高度集合只有一个值，就是钉这一条。
>
> 悬停 `group-hover:scale-105`：`contain` 下放大 5% 先吃自己的留白，长图也不会被裁。
>
> 详情弹层与卡片**必须同一套**：卡片 contain、弹层 cover 的话，点开一张图会看到"另一张照片"。
>
> **标题手机三行、桌面两行。** 手机卡宽只有 169px、字号 13px，两行加起来约 20 个字符，长名字等于被砍断；三行能放约 30 个字符，`min-h-[54px]` 保证短名字的卡片也占同样高度、网格不错位。桌面 260px 宽 + 15px 字号，两行已有约 40 个字符，再多只是浪费高度。两端都带 `title` 属性，桌面悬停可看全名。

### 详情弹层：图文分离

以前整个弹层是**一条滚动流**：图片在上面，规格在下面。选了五六个颜色、七八个尺码的款，
滚到规格区时图片早就出屏了 —— 点「Black」看不到黑色长什么样，只能再滚回去，再滚下来。

现在按宽度分成两套布局，**同一份 DOM**：

| 条件 | 布局 |
|---|---|
| `split`（桌面 ≥1024，或 ≥768 且横屏） | 左右双栏：左图固定、右信息独立滚动，操作条贴在右栏底部 |
| 其余（手机竖屏、平板竖屏） | 单列：图片 `sticky top-0`，规格从图片下面滑过 |

`split` 是 `tailwind.config.js` 里自定义的 screen。加横屏条件是因为 844×390 的手机横过来
宽度足够放两栏，竖着堆只会把规格压进一条 150px 高的滚动带。

**同一份 DOM 怎么变成两栏**：滚动容器在 `split` 下 `display: contents`，它自己不再生成盒子，
两个孩子（图片、信息）直接成为网格子项 —— 图片跨两行占左列，信息占右列第一行，操作条
`col-start-2 / row-start-2` 贴在它下面。没有复制图片节点，也就不会有两次 640w 请求。

**手机端的吸顶会收缩，但不是每次都收**：

- 往下滚过 56px 吸住、回到 24px 以内还原（两个阈值，同一个会立刻抖回来）
- 吸住时从 `clamp(180px, 36vh, 380px)` 收到 `clamp(160px, 30vh, 260px)`
- **只有内容超出 ≥100px 才收**。门槛 = 吸住阈值 56 + 收缩量约 40：低于它，收掉的高度
  会连同滚动行程一起消失，用户滚到一半发现页面往回缩了 40px。够不到门槛就只吸住、不收。
- 吸住后加一条 1px 分隔 + 轻阴影，让"内容滑到图下面"看起来是设计而不是渲染错误

**换图是交叉淡入**，见上一节 `CrossfadeImage`：旧图在新图载入前一直留着，所以换色
不会出现白闪；旧图淡出 300ms 后卸载，DOM 始终只有一张图（`smoke:gate [5ac]` 断言这一点）。

横屏不重排、不溢出：`smoke:gate [5ac]` 在 1280×800 / 375×568 / 844×390 三种尺寸下各断言一遍
（双栏几何、吸顶位移、收缩、换图、无横向溢出）。

### 分类、搜索、分页怎么配合

**顺序是死的：先过滤，再分页。** 分页永远是最后一刀，切在"当前分类 + 当前搜索词"的结果上，不是切在全部商品上。

```
catalogue（去掉 hidden）→ 分类过滤 → 关键词过滤 → .slice(0, limit)
```

这条顺序反过来的后果是实打实的：先切 24 个再搜「P9B043」，如果它排在第 100 位，搜出来就是空的 —— 而且看起来像"没这个货号"。`test-catalogue.mjs` 里留了一组对照断言专门盯这件事。

其他规则：

- **换分类或改搜索词，批次回到 24**。否则从 137 个的分类切到 5 个的分类再切回来，会突然显示 137 个。
- **分页只切渲染，不动计数**。分类 chip 上的数字是这一类总数，`Showing 24 of 136` 里的 136 也是这一类总数，不是"已经加载了几个"。
- **换筛选时如果已经滚过 300px，回到页面顶部**，避免停在一个突然变短了的页面中间。
- 搜索只匹配**货号 + 名称**。ASIN 搜不了 —— 前台根本拿不到 ASIN 表（那张表是白名单可读），这是设计如此，不是漏做。
- 页脚和 `Admin Login` **在分页按钮下面**，不随加载次数往下跑。加载完全部商品后按钮消失，页脚就是最后一个元素。

### 前台排序：四档（在售角标 → 在售 → Coming Soon → 隐藏）

**四档，档内各自保持后台排好的 `sort_order`。这一层纯粹是渲染时算的，库里一个字节都不动。**

| 档 | 谁 | 档内顺序 |
|---|---|---|
| 1 | **在售** 且 有普通营销角标（New / Best-seller …） | `sort_order` |
| 2 | **在售** 且 没角标 | `sort_order` |
| 3 | **Coming Soon**（不论有没有角标） | `sort_order` |
| 4 | 隐藏（`hidden = true`） | `sort_order` |

```
后台 sort_order:  A(–) B(–) C(New) D(–) E(Best-seller) F(–) X(Coming Soon) Y(New, Coming Soon) Z(hidden)
前台:             C E | A B D F | X Y | (Z 不出现)
```

#### 为什么 Coming Soon 从第一档挪到了第三档

它本来跟角标商品一起排在第一档 —— 预告带角标，角标规则赢了。运营反馈的结果很直接：
**首屏全是买不了的款，红人会以为这家没货，还没往下滑就走了。**

所以现在的规则是「首屏必须全部可加购」。预告并没有消失，只是沉到在售商品后面：
往下滑就能看到，起到预热作用，而不是挡在门口。

代码里是 `storefrontOrder` 的四桶稳定分区（`utils/catalogue.js`）：

```js
storefrontTier(product)   // 1 | 2 | 3 | 4，单独导出，测试直接断言档位
storefrontOrder(list)     // 一次遍历入四桶 → concat，档内顺序即输入顺序
```

**是分区，不是 `sort()`**：storefront 的 product 形状里根本没有 `sort_order`（它在
`orderById` 里单独维护），所以写不出 comparator，也就不可能把运营拖好的顺序排乱。

#### 秒杀为什么不参与排序

`hasBadge` 只看 `tag`，所以带有限时秒杀但没有营销角标的商品在第 2 档，不会置顶。
这是刻意的：秒杀是时间函数，拿它当排序依据，货架会在每个活动开始/结束时自己重排一次，
而且排出来的顺序取决于时钟而不是运营的拖拽。`test:catalogue [14]` 有一条专门钉这个。

#### 第 4 档仍然不渲染

`hidden` 在这个系统里的含义是「还没发布」，不是「排在最后」。前台在排序之前就把它滤掉了
（`SelectionPage` 的 `SHOW_HIDDEN_PRODUCTS = false`）。原因很实在：批量导入的新货号默认
`hidden = true`，如果隐藏＝仍展示，那么每导入一批新货，没补完图、没配 ASIN 的草稿就会
全部出现在红人眼前，还能被加购。引擎保留第 4 档只是为了让「万一传进来」也不会插在中间。

#### 几个仍然成立的细节

- **只能改前台**：后台列表永远按 `sort_order` 排，拖拽不受影响（`smoke:gate` 的 `[5p]` 钉着）
- **和分类、搜索叠起来**：先按分类 + 关键词筛，再分档，最后才分页
- **角标只看文字**：`tag` 为空就不算（只设了颜色没写字，卡片上本来就没有 pill）
- **清空角标 / 取消 Coming Soon 立刻归位**：排序每次渲染重算，不落库
- **排在 191 位也能上第一屏**：排序发生在分页**之前** —— 实测 7 个带角标的商品里有 3 个
  排在 191/194/196 位
- **首屏断言**：`test:catalogue [15]` 造 60 个商品、把 10 个预告放在输入最前面，
  断言 `slicePage(order(list), 24)` 里**一个预告、一个隐藏都没有**

觉得角标块太占首屏的话有三个降级开关（只在 All 视图生效 / 只置顶前 N 个 / 后台开关），
都只改 `SelectionPage` 一行，见 HANDOVER §23.7。

### 限时秒杀（Limited Deal）

商品级的时间窗，纯前端计算：运营只点两个日期，到点角标和价格自己出现、自己消失。
**没有定时任务、没有网络请求、也不需要发版。**

#### 两处入口，两种信息密度

| 位置 | 常规目录（All / 分类） | ⚡ Limited Deals 专区 |
|---|---|---|
| 卡片角标 | `Limited Deal` / `25% OFF`（两行，红） | 同左 |
| 卡片价格 | **不显示** | `$15 – $25` |
| 排序 | 后台拖拽序（不按时间） | 进行中按"最快结束"，排期中按"最快开始" |

常规目录不显示价格是刻意的：169px 宽的卡片已经有图、名字、亚马逊链接、规格行和按钮，
再塞一块价格会让所有秒杀卡片比邻居高一截，网格变成补丁布。折扣写在角标里足够，
数字留给"价格就是重点"的那个 Tab。

专区只在**有秒杀时**出现（`Limited Deals (3)`），常驻一个空 Tab 比没有更糟。

#### Tab 的名字可以改（黑五叫 Black Friday Deals）

名字存在 `settings` 表（`deals_tab_label`），默认 `Limited Deals`。后台商品列表页顶部有一行：

```
DEALS TAB  [ 🔥 Black Friday Deals      ]  [ Rename ]  [ Reset ]
```

- 改完立刻生效：前台顶部那枚药丸在**下一次渲染**就换名（realtime 订阅 `settings` 表，
  已经打开着的页面也会跟着变，不用刷新）
- 空字符串 = 恢复默认；`Reset` 也是同一个动作
- emoji 原样保留（`🔥` 不会被"清洗"），上限 32 字
- 这个值**只能来自数据库**：localStorage 只存在于运营那台电脑，写死常量又要发版 ——
  而它必须让红人的手机也看到


专区里只收「进行中 + 排期中」；已结束的会退回普通商品，Coming Soon 的一律不收
（买不了的折扣不算折扣）。

#### 折扣区间筛选

专区顶部有 4 个桶：`10% - 20%` / `20% - 30%` / `30% - 40%` / `40%+`，加一个 `All deals`。

- **左闭右开**，和日期窗口同一套约定：恰好 20% 属于 `20-30`
- **按最大折扣归类**：`20% - 50% OFF` 的进 `40%+`
- **低于 10% 不落桶** —— 它是秒杀，但不是好价，只在 `All deals` 里出现
- 桶读的是**角标上那个数字**（`discountOf`），不是另算一遍，所以不会出现
  "卡片写 50% OFF、却在 10-20 桶里"

#### 折扣是怎么算出来的

后台填的是自由文本，`39.99` 或 `30-50` 都行。`autoDiscountLabelFor` 的做法：

```
取两边的所有数字 → 各自取 min/max（区间）
最低折后价 ÷ 最低原价 → 最深折扣（min）
最高折后价 ÷ 最高原价 → 最浅折扣（max）
min === max ? "25% OFF" : "20% - 50% OFF"        // 都夹在 0–99
```

**低对低、高对高**，不是交叉配对。`30-50` 配 `15-25` 算出来是 `50% OFF`（两端都五折），
而不是 `20% - 50%` —— 交叉配对会得出 17%–70%，那是数学包络，不是顾客看到的价格档位。

| 原价 | 折后价 | 结果 |
|---|---|---|
| `39.99` | `29.99` | `25% OFF` |
| `30-50` | `15-25` | `50% OFF` |
| `30-50` | `15-40` | `20% - 50% OFF` |
| `100` | `120` | 空（不印负数） |
| `0` | `10` | 空（不除零） |

**自动 ≠ 强制**：原价/折后价失焦时自动写入 `discount_label`；一旦运营手动改过，
就再也不会被覆盖（`labelTouched`），旁边给一个 `Use auto` 退回自动值。

#### 日期选择器

后台是两个原生 `<input type="date">`，只点日期。保存时补时刻：
**开始日 `T00:00:00`，结束日 `T23:59:59`** —— 这样"10/28 到 10/30"是完整三天，
而不是 30 号零点就结束（少一天，且运营不会想到）。

> ⚠️ 老数据里带具体时刻的值（`2026-10-28T10:00`）在后台**第一次保存后会被规范成
> 00:00:00 / 23:59:59**。这是日期选择器的必然结果，卡片上有一行提示说明。

#### 时间怎么解析

- 存的就是运营点的那两个日期，`text` 列，入库/出库都不换算
- 解析先走严格正则再本地构造并**回读校验**，`2026-02-31`、`24:00` 这类会被构造器
  「进位」的脏值直接判无效
- 交付 `new Date('2026-10-28 10:00')` 不行：V8 认空格，Safari 历史上返回 Invalid Date，
  失败表现是"秒杀永远不生效"且不报错
- 窗口**左闭右开**：填 `10-30`，那天 23:59:59 之后结束

#### 排期中（Scheduled）也要能看见

排期中的商品进专区、出角标、可以提前加购；到点同一个 ticker 自动切成 `ends in`，
不刷新页面。

#### 倒计时只在 24 小时内才数秒

一场提前一周排期的活动，秒针每秒跳一下既没有信息量，又让人误以为马上开始：

| 距离 | 排期中 | 进行中 |
|---|---|---|
| **> 24 小时** | `Deal starts in 6 days` | `6 days left` |
| **≤ 24 小时** | `Deal starts in 05:12:33` | `Deal ends in 05:12:33` |

- **向下取整**：25 小时是 `1 day`。差 23 小时时突然从「1 day」掉到 `23:59:59`，
  读起来就是"马上要结束了"，这正是想要的紧迫感
- **恰好 24 小时走时钟**（需求是「<= 24 小时」）
- 归零那一格不立刻消失：先换成 `Deal ended` 停 1.8 秒再收起（`justEnded`），
  `animate-fade-in` 让"开始/结束"两次切换是**换**过去的，不是跳过去的
- 跨过 24 小时那条线、或排期中转进行中时，`key` 带上 `phase + mode` 让 React 重挂
  这一格，动画才有机会重播

倒计时只在详情页跑（一个 `setInterval`，归零自清、卸载清理）。卡片不挂定时器：
24 张卡 24 个 interval 不值当，卡片过期要等下一次渲染。

#### 没折后价就不出价格区

只出角标。一个没有数字的"五折"比不写更糟。

**一个商品一个价**，不分颜色/尺码 —— 要按变体定价得把价格挪进 `specs` 或新建 jsonb，
那是另一套数据结构，本轮没做。

**没跑 `supabase/09-deal.sql` 也不会崩**：五列是可选列，探测失败就从 select 和写入里一起
剔掉，后台卡片会显示琥珀色提示（原文 + 该跑哪个 SQL）。

#### 专区置顶（`deal_priority`）

秒杀专区的默认顺序是「越急的越前」（进行中按最快结束）。黑五需要把主推钉在最前面，
所以多了一个权重列：

```
deal_priority 降序 → 进行中早于排期中 → 结束/开始时间升序 → 后台拖拽序
```

- **只在 ⚡ Limited Deals 里生效**，常规货架仍按 `sort_order` —— 货架不该因为一场活动自己重排
- 权重放在时间之前，因为它是运营的**决定**，时间是**状态**；反过来，"我钉住的第一个"
  会在十分钟后被一件更早结束的商品顶下去
- `0` = 不置顶（默认值，迁移不需要回填）；负数按 0 处理
- 单件在编辑器 Limited Deal 卡片里填，批量在 `Batch Edit Deal` 的 `Pin` 里填
- 同样依赖 `supabase/11-sub-badge-deal-priority.sql`

#### 批量导入秒杀（`Import Deals`）

后台顶部的 `Import Deals`（秒杀图标）读 CSV / XLSX，按**货号**匹配后写五个 `sale_*` 列。
两种表头都能直接拖进去，列顺序随意：

```
A. 货号      | 原价 | 折后价 | 开始日期 | 结束日期
B. 主卖货号  | 秒杀价 | 折扣率 | 开始日期 | 结束日期      ← 运营导出的那种
```

- **货号**：`主卖货号` / `货号` / `款号` / `sku` 都认
- **价格**：`秒杀价` / `折后价` / `折扣价`；`原价` / `original price`
- **折扣率** → `discount_label`：`30%` / `30` / `0.3`（Excel 百分比格式读出来是小数）
  统一写成 `30% OFF`。没有这一列就留空，前台按两个价格自己算
- **原价可以没有**。没有这一列、或者这一格空着 → `original_price` 写 NULL，
  前台**只显示秒杀价 + 折扣率，不显示划线价**（详情页的 `priceInfo.was` 本来就有空值守卫）。
  但"有这一列、写了东西、却读不出来"仍然算错误行 —— 那是打错字，静默丢掉会让人以为导进去了
- **日期**：`YYYY-MM-DD`，自动补成 `T00:00:00` 和 `T23:59:59`（结束日算整天）
- 确认前预览会显示「匹配成功 / 未找到货号 / 格式问题行」，外加「N 行没有原价」的提示
- `折扣率` 一旦存在就**优先于价格计算**（`discountOf` 的第一优先级），所以角标、
  专区 10/20/30/40% 分桶都跟着运营填的数字走 —— 没有原价时也只有它说得清便宜了多少

### ACC 佣金（Amazon Creator Connections）

两列，一个开关一个数据：`has_acc boolean not null default false`、`acc_id text`
（`supabase/10-acc.sql`）。

**为什么这里要布尔列，而秒杀没有**：秒杀的"开"能从"两个时间非空"推出来，多一个
`is_deal` 只会多一处「开关关了但时间还在」的中间状态；ACC 没有可推导的东西 ——
Campaign ID 可以先空着（活动还没批），也可以先填好再开。所以必须有一个独立布尔值
回答"现在对红人展示吗"。

| 位置 | 表现 |
|---|---|
| 卡片角标 | **不再有** —— 佣金是点进去才判断的事，详情页有一整块 ACC 卡片 |
| 详情页 | 一张琥珀色小卡：活动说明 + Campaign ID + `Copy ID` 一键复制 |
| 后台 | `Amazon Creator Connections` 折叠卡：开关 + Campaign ID 输入框 |

**ACC 只出现在详情页**：卡片上那枚在 169px 的宽度里只是噪音，而详情页有一整块
ACC 卡片（活动说明 + Campaign ID + 复制按钮）。详情页的角标栈里它仍然是第一行的
候选之一，顺序见「角标颜色」一节。

**开关关掉不会清空 `acc_id`**：ID 是拿不到第二次的运营资产，误点一次就让人回亚马逊
后台重抄一遍，是小损失里最恼人的那种。前台只认 `has_acc`，所以"关掉"依然是真的关掉。

**没有 ID 也能开**：活动批下来但 ID 还没抄进来时，角标照出（红人知道这单有佣金），
详情页的卡片写 `Still pending`，复制按钮置灰而不是消失 —— 一个悄悄少了个控件的卡片
看起来像坏了。

**没跑 `supabase/10-acc.sql` 也不会崩**：两列是可选列，探测失败就从 select 和写入里
一起剔掉，后台卡片出琥珀色提示。

### 新手引导（右下角 `?`）

第一次进站会自动弹一次五步引导，之后随时点右下角的 `?` 重看。**零图片、零请求**：
五个步骤图形和那个问号全部是 div + 边框画的，没有任何 SVG、图标库或字体。

| 步骤 | 图形（CSS） |
|---|---|
| 01 Select Category | 2×2 小方块，右下角选中 |
| 02 Choose Pieces & View Spec | 放大镜：圆环 + 45° 柄 |
| 03 Size, Color & Selection | 三枚叠在一起的色卡 |
| 04 Review and Generate Code | 三条购物行，最后一条是 accent |
| 05 Copy and Send Code | 两张错位的纸 |

**为什么是单步切换而不是一页滚到底**：五段文案叠成一页，390px 宽的手机上必然要滚，
而"引导里还有滚动条"会让人以为没看完，Next 还可能被推出视野。单步每屏约 300px，
重点永远在一屏内。代价是多点四次，用底部进度点和 `01 / 05` 抵掉。

- **什么时候弹**：骨架屏结束之后 500ms。加载中弹等于用遮罩盖住加载态，加载失败也不弹
  （那一屏是重试按钮）
- **记在哪**：`localStorage` 的 `mako_seen_guide_v1`，值是版本号 `v1`——不是 `true`。
  改文案就把版本 +1，所有人再看一次
- **只在关闭时写**：刷新到一半不算"看过"。Skip / Got it / ✕ / 点遮罩 / Esc 五条路
  走同一个 `close()`
- **滚动锁是引用计数的**：`useScrollLock` 模块级计数，最后一个遮罩关掉才还原 `overflow`。
  两份实现在"引导开着、商品弹层也开着、先关一个"时会把背景提前解锁
- **移动端**：卡片 `max-h-[86vh]` 内部可滚（横屏也不会切掉按钮），正文区定高
  `min-h-[92px]`，翻页时卡片不跳
- **可访问性**：`role="dialog" aria-modal`、打开时焦点落在 Next、`Tab` 在卡片内循环、
  `←/→` 翻页、`prefers-reduced-motion` 下只保留淡入

> 浏览器测试要注意：Playwright 每个上下文都是空 storage，等于"首次访问"，
> 引导会盖住网格。所以 `scripts/unlock.mjs` 有 `skipGuide(page)`，各 smoke 脚本
> 在 `newPage` 之后立刻调用；`smoke:gate [5y]` 故意不调，专门测真实的首次访问。

### 一键清空

抽屉底部的 `Clear all` 只在有商品时出现，点一下原地展开确认：

```
Are you sure you want to clear your selection?
2 variants · 2 items will be removed.
```

`.env` 里必须有的两项（Supabase → Project Settings → API）：


`npm run push`、`smoke-gate.mjs`、`shots.mjs` 都靠这两项登录。缺了它们，前两个会直接跳过并提示，不会报错退出。

## 五、商品数据

### 数据在哪

**线上以 Supabase 为准。** `src/data/products.js` 现在有两个用途：

1. 首次导入的种子（`npm run push` 读它写进云端）
2. 后台 **Copy as products.js** 导出后的对照备份

改商品请在 `/#/admin/products` 里改，或者改 `data/*.js` 后重新 `npm run push`。**直接在 `data/products.js` 里改而不 push，线上不会变** —— 这是从 localStorage 时代迁移过来最容易搞混的一点。

### 字段

`src/data/products.js` 里的每个商品（也是后台导出的形状）：

```js
{
  id: 'p001',                        // 内部唯一标识，稳定不变
  sku: 'AMZ-1003',                   // 货号（表格里的原值），可省略
  name: 'AMZ-1003',                  // 展示名，导入时默认 = 货号
  category: 'Uncategorised',         // 决定出现在哪个栏目
  image: './placeholders/placeholder.svg', // 或任意图片 URL
  specs: {                           // 可省略（则视为 one size）
    Colour: ['Black', 'Oatmeal'],
    Size: ['S', 'M', 'L'],
  },
  variantImages: {                   // 可省略：每个选项自己的图片
    Colour: {
      Black: 'https://cdn.example.com/hoodie-black.jpg',
      Oatmeal: 'https://cdn.example.com/hoodie-oatmeal.jpg',
    },
  },
  soldOutVariants: ['Green|S'],      // 可省略：这些组合断货，键同 asins.variants
  hidden: true,                      // 可省略：true = 暂时下架，前台看不到
  tag: 'New',                        // 角标，可省略
  isTeaser: true,                    // 可省略：Coming Soon，可见但锁尺码、不可加购
  saleStart: '2026-10-28T10:00',     // 可省略：秒杀开始（本地时间字符串）
  saleEnd: '2026-10-30T22:00',       // 可省略：秒杀结束（左闭右开）
  salePrice: '19.99',                // 可省略：折后价，纯文本
  originalPrice: '39.99',            // 可省略：原价，纯文本
  discountLabel: '50% OFF',          // 可省略：折扣标签
}
```

### 后台语言（中文）

后台给运营团队用，前台给海外红人用 —— 两边受众完全不同，所以**只有后台是中文的**。

- 字典在 `src/i18n/admin.js`：一个扁平对象（英文原文 → 中文）＋ `t(text, vars)`
- **零依赖**：需要的只有"查表 + `{name}` 占位符替换"，`i18next` / `react-intl`
  会给主包加上几十 KB 和一套 provider
- **key 是英文原文**：`t('Cancel')` 读起来就是那一行 UI。代价是改英文原文要改 key，
  但这里的英文原文已经不再是展示文案，只是 key
- **查不到就显示原文**（不是 `admin.cancel` 这种占位符）：新增文案忘了翻译时，
  后台只是多了句英文，看起来不像坏了；`scripts/test-admin-i18n.mjs` 会把它们扫出来
- **带插值的提示直接写中文**（`` `已给 ${count} 件商品设置角标` ``）：这类句子没有
  "英文原文"可当 key，放进字典只会让 key 变成一句模板
- `aria-label` / `title` / `data-*` **保持英文**：它们不进可见文案，却是无障碍与
  冒烟的稳定钩子。可见文案（按钮、标签、占位符、提示、弹窗标题）才翻译

**红线：前台一个 `t()` 都不许引，一个汉字都不许出现。**
`test-admin-i18n.mjs` 会做三件事：字典自检（无重复 key、每条都有中文）、扫后台源码里
还没进 `t()` 的英文、以及**去掉注释后扫前台源码里的汉字**。最后一条是这条测试存在的
真正理由 —— 后台汉化最典型的翻车方式是"顺手改了一个共用组件"，于是红人在商品卡上
看到「已售罄」。

### 上架 / 隐藏（`hidden`）

- 字段**缺省即为在售**，只有明确写了 `hidden: true` 才算下架
- 下架的商品**不删数据**：前台列表、栏目数量、购物车预览、新生成的码里都没有它，但它仍在商品库里，所以**已经发出去的旧码解码时照样显示名称和图片**
- 和「彻底删除」的区别：删除是不可逆的，历史码里那一行会变成 `Removed product (p001)`；隐藏只是看不见，随时可以再打开

### 单变体断货（`soldOutVariants`）

只让「某个颜色 + 某个尺码」不可选，商品本身照常上架。存的是**组合级**清单：

```js
soldOutVariants: ['Green|S', 'Green|M']   // 键和 asins.variants 完全一致
```

**为什么是组合级，不是颜色级**

真实断货永远是 SKU 级的 —— 最先卖完的是某个尺码。只记颜色的话，标了 `Green` 就会把还有货的 `Green|L` 一起干掉，那等于少卖一个 SKU。

「整个颜色断货」在界面上是**批量动作**（点一下列头 = 写 N 个键），不是第二种存储格式。一种表示意味着一处判断「有没有货」，没有优先级规则要记。

**键的格式**：`variantKey(colour, size)` → `` `${colour}|${size}` ``，见 `src/utils/sku.js`。`asins.variants`、`product_links`、`soldOutVariants` 三处共用同一套键，所以「这个组合有没有 ASIN」和「这个组合有没有货」查法一致。one size 商品的 size 段为空，键是 `Green|`。

**断货判断是上下文相关的，不是每个选项一个静态标记。**

颜色先选、尺码后选，所以：

- `Green` 只有在该颜色的**所有**尺码都断时才禁用；断了一半的 `Green` 仍然可选，点进去再看到具体哪些尺码灰掉
- `M` 只在**已选颜色**的 `M` 断时才禁用 —— 选了 `Green`，`M`/`S` 灰、`L` 仍可选；不选颜色时 `M` 只要还有任一颜色有货就可用

这套规则在 `isOptionAvailable(product, specs, type, value)` 里，`scripts/test-sold-out.mjs` 用「选 Green 后 M/S 禁用但 L 仍可选、Black/M 不受影响」钉住它。

**断货不进选款码。** 断货是库存状态，不是红人的选款内容，所以 `utils/code.js` 一个字没动。已经发出去的码解码后仍显示原颜色/尺码，只是前台不再允许新选它。

**前台三处表现**

| 位置 | 表现 |
|---|---|
| 详情弹层 | 断货选项置灰 + 删除线 + `(Sold out)`，点不动 |
| 商品卡片 | 只有**全部组合**都断时才加白色 `Sold out` 角标；卡片仍然可以点开（能看到哪些尺码还有货） |
| 购物车 | 断货行标红 + `Sold out` 标签，`Edit` 换成 `Remove`；底部红色告示 + `Remove sold-out items` 一键清掉；`Generate my code` 在有断货行时禁用 |

**已选之后才断货**的处理是「拦住 + 一键移除」，不自动删：红人可能正想换个尺码，悄悄把行删掉会让她以为是自己点错了。

**列不存在时也能启动。** `productStore` 请求里带着 `sold_out_variants`，如果 `05-sold-out.sql` 还没跑，PostgREST 会返回 400 —— 检测到错误里含这个列名就把标志位置 false、退回旧列重查，并 warn 一句。效果等价于「全部有货」，和 `linkStore` 对缺 `product_links` 视图的容忍一致。代价是那一次请求会在控制台留一条 400，跑完 SQL 就没了。

### 变体图（`variantImages`）

红人在详情弹层里点「Black」，主图就换成黑色那张；点「Oatmeal」换另一张。没配的颜色自动用 `image`，所以**永远不会出现裂图或空白**。

结构是「规格类型 → 选项值 → 图片 URL」两层：

```js
variantImages: {
  Colour: { Black: 'https://…/black.jpg', White: 'https://…/white.jpg' },
}
```

- **只存 URL，不存 base64。** 一张 base64 图动辄几百 KB，塞进 JSON 字段里会让每次读商品都拖上几 MB，Realtime 推送也会被撑爆。所以编辑器里没有上传入口。
- **可缺省。** 只配了 3 个颜色，剩下 4 个照常走默认图。
- **按类型查找，颜色优先。** 同时配了 `Colour` 和 `Size` 的图时，切换颜色优先命中颜色图。
- **大小写容错。** 手写 `black` 而选项是 `Black` 也能匹配上。

**切换逻辑**

前台任何位置要显示一张商品图时，都调 `resolveProductImage(product, 已选规格)`：

1. 从 `已选规格` 里取出所有有值的项，**颜色排在最前**
2. 依次去 `variantImages[类型][值]` 找 URL —— 先精确匹配，再忽略大小写匹配
3. 找到就用它；没找到用 `product.image`；再没有用 `placeholder.svg`

这个函数是纯函数，卡片、详情弹层、购物车预览、后台查询结果共用同一套逻辑，不会出现「卡片换了图但购物车没换」这种不一致。

拿到 URL 后交给 `<ProductImage>` 渲染，它维护一条 `[变体图, 主图, 占位图]` 的链，**任何一级加载失败（onError）就自动往下降一级**。所以就算某张图 URL 失效、域名挂了、或者填错了一个字，看到的是主图而不是裂图图标。

「立即切换」靠的是 React 状态：详情弹层里点颜色 → `setSpec` 触发重渲染 → 重新算 `resolveProductImage` → 换成新 URL。

**换的那一下不是硬切。** 直接改 `src` 会让浏览器先清空画布，白底商品图上就是一次白闪。`CrossfadeImage` 把新图先用游离的 `Image()` 预载（旧图继续显示），载入后垫在下面、旧图在上面淡出 300ms，淡完卸载 —— 任何一帧截下来都是合法画面。`prefers-reduced-motion` 下直接换。

**但列表页的卡片图不跟着变。** 卡片永远渲染 `product.image`，不传已选规格。理由：列表页是红人"认款"的地方，图一动她就找不到刚才看的是哪一件了；而且卡片上可能同时挂着这个款的好几个颜色组合，用哪一张都不对。切色换图只发生在详情弹层里。`scripts/smoke-live.mjs` 的 `[2] Card image` 专门盯这一条 —— 在弹层里点完颜色后，回头断言卡片的 `src` 一个字符都没变。

**导入时会被保留。** `npm run catalog` 重新导入表格时，`variantImages` 会跟着旧目录带过来，并且只保留「表格里仍然存在的颜色」——已经删掉的颜色，它的图也会一起清掉，不会留孤儿数据。想彻底重置用 `--fresh`。

**两个标识，各管一件事**

| 字段 | 是什么 | 谁在用 |
|---|---|---|
| `id` | 内部标识，`p001` 格式，导入时分配一次，之后永不改变 | 选款码、程序内部 |
| `sku` | 货号原文（可能带空格、斜杠） | 后台列表、ASIN 映射、导出订单 |

### 亚马逊链接（卡片 + 详情弹层）

商品名下面那行 `View on Amazon ↗` 由货号推出来：取该商品**第一个** ASIN，拼成 `https://www.amazon.com/dp/{ASIN}`，新标签页打开（`rel="noopener noreferrer"`）。

- 数据来自 `product_links` 视图，**不是**前端包里的快照。后台改了货号，前台下次刷新就是新链接。
- 没有任何 ASIN → 链接位显示 `Listing not linked yet`，点不动，也不会渲染一个空 `href` 出来。
- 详情弹层里同一个链接，另加一句提示：选中的颜色/尺码没有对应货号时显示 `No listing linked for this colour / size yet. Your contact can confirm stock before it ships.` —— 这是**提示**不是错误，红人照样可以加购，运营收货号时再确认。

### 已删除的颜色不会复活

后台在编辑器里删掉一个颜色后，前台有三道防线：

1. **加购时**：`sanitizeSpecs` 把不在 `product.specs` 里的值直接丢掉，选不出来的组合加不进购物袋
2. **刷新时**：`reconcileLines` 用当前目录重算每一行的唯一键，变体已消失的行整行移除（`reason: 'variant'`），不会留下"半行"
3. **编码时**：清洗后不再完整的行**直接丢弃**，不会把剩下的半边编进码里

第 3 条是关键：`{Colour:'Charcoal', Size:'M'}` 清洗后只剩 `{Size:'M'}`，那**是另一个组合**，不是红人选的那个。宁可少一行让她重选，也不能静默换成别的款发出去。

浏览器里存的是 `mako_lines_v1`。更早的 `mako_selection_v2` / `mako_specs_v2` **直接删除，不做迁移** —— 迁移会把一个可能已经被删掉的颜色带进新版，正是要避免的事。

后台解析历史选款码时，遇到已删除的颜色**照常显示文字**（`Charcoal / M`），只是 ASIN 列显示 `No matching ASIN`，不报错、不整码失败。

分开的好处：货号里出现空格或 `/` 不用被改写成 id；改货号也不会让已发出的选款码失效。

**没有价格、没有卖点文案、没有长描述** —— 这是选款单，价格与对接人另行确认。卡片上展示的是颜色和尺码，不是价格。

### 栏目（分类）

分类清单在同文件的 `categories` 导出里，是**出厂默认值**：

```js
export const categories = ['Tops', 'Knitwear', 'Dresses', 'Bottoms', 'Outerwear', 'Shoes', 'Accessories']
```

这份清单可以在后台直接改（增、删、改名），改动写进 `categories` 表，**所有人的前台几秒内跟着变**。三处逻辑：

1. **前台导航按「商品实际用到的分类」生成**，顺序跟随上面的清单。某个分类下的商品全删了，该栏目自动消失；商品上出现清单里没有的分类（手填的），也照样显示，只是排在最后
2. **改名会连带改商品**。把 `Uncategorised` 改成 `Tops`，原来属于 `Uncategorised` 的商品会一起改过去，不会出现「分类没了、商品悬空」
3. **改名撞到已有分类就合并**。把 `Uncategorised` 改成 `Tops` 而 `Tops` 已存在时，两个合并成一个，不会出现同名两栏

`Uncategorised` 是兜底桶，删不掉：只要它下面还有商品，删除按钮会拒绝并提示先把商品挪走。

**为什么分类要单独一张表**：商品数据来自导入，分类却是运营随时会调的东西。混在同一张表里，改个分类名就得重跑导入。

### 替换要点

1. `id` 必须唯一且稳定 —— **导入后不要再手工改 id**
2. 选款码存的是 `id`，所以**调整顺序、删除商品都不影响历史码**（v3 起）
3. 货号（`sku`）可以随时改，改完历史码里的 id 仍能对上，导出会显示新货号
4. 图片**任何比例都能用，且永远完整不裁**：正方形画框 + `object-contain` + 纯白底，非正方形的图按自身比例缩放居中，多出来的部分是纯白，和原图背景同色所以看不见。**但这不等于"商品一样大"** —— 0.43 的长裤在 260px 画框里只占 112px 宽，视觉上就是比 0.96 的内衣小一半。要让大小统一，唯一的办法是在**源图**上解决：统一裁成正方形、商品占画面 80% 左右、白底拍摄。CSS 只能保证不裁，救不回拍摄比例不一的照片。

商品数量没有硬上限（v3 不再用位掩码）。每款数量上限 35。

## 六、商品编辑器（`/#/admin/products`）

不需要改代码就能维护商品，改动写入云端，**所有人（含其他同事的后台）几秒内自动刷新**。

**能改什么**

- **货号**：对应表格里的原值，改完 ASIN 映射和导出会立刻跟上；内部 `id` 不受影响
- **主图**：填图片 URL，**或者把下面任意一张颜色图片卡片拖到这个预览框上**（松手即替换，toast 会说明来自哪个颜色）
- **去亚马逊**：主图 URL 下方一枚 `View on Amazon` 链接，新标签页打开这个商品的 listing（`amazon.com/dp/{第一个有效 ASIN}`），补图时不用再回前台找链接（见下面「补图：不用离开后台」）
- **分类**：输入框 + 下拉建议，可以选已有分类，也可以直接手打一个新分类
- **上架开关**：`Visible on storefront` 一拨就下架，再拨回来就上架
- **断货开关**：`Stock` 网格里勾单个颜色/尺码组合，只让那个组合不可选，商品照常上架
- **颜色 / 尺码**：任意数量的规格组，每组任意数量的选项，可随时增删
- **ASIN 映射**：编辑器**最右一列**（窄屏在规格区下面）常驻展开、不能折叠，每个颜色 × 尺码一个输入框。
  在左边新加一个颜色，这里立刻多出一组空行（带琥珀 `new` 标记），贴好 ASIN 点保存即同时写
  `products` 与 `asins` 两张表 —— 不需要另外一次"保存 ASIN"
- **每个颜色的图片 URL**：Colour 组下每个选项都带一个输入框，填完旁边立刻出缩略图预览
- **名称、角标**
- 新增商品、删除商品、上下移动排序
- **搜索**：一个输入框同时匹配货号、ASIN、名称和 id；粘一列货号也能批量筛（见「批量搜货号」）；右侧下拉按分类筛选
- 从云端重新拉一次（`Refresh from the cloud`，socket 掉了时的兜底）

**只支持图片 URL，没有上传入口。** 早期版本会把上传的文件转成 base64 存进浏览器，几张图就把 5MB 配额撑满、保存直接报错。现在输入框只收直链，一个 URL 大约 60 字节，还能被浏览器和 CDN 缓存。老数据里如果还留着 base64 图，编辑器会提示「Legacy uploaded image」，点 Clear 清掉换成 URL 即可。

**颜色图片怎么填**：在 Colour 组里，每个颜色一行 —— 左边缩略图（实时预览）、中间颜色名、下面一行图片 URL。留空就是这个颜色用主图。填了几个颜色，底部会显示「N colour photos set」。

**反过来也只要一秒**：觉得某个颜色的图比主图好看，**按住那张卡片拖到左上的主图预览框**——

```
悬停时：预览框亮起描边 + "Drop to use as main image"
松手后：主图 URL 换成那张图，预览立刻更新，toast "Main image updated from Black variant"
```

- **整张卡片都能抓**，不只缩略图；卡片里的输入框照常打字（从输入框发起的是文本选择，不是拖拽）
- 拖完还能改字、改色、改 URL —— 模板/拖拽都只是起点，不是锁
- 重复拖同一张会提示 `Black is already the main image`，不会假装做了事
- 没配图的颜色也能拖，掉下来会明说 `Black has no photo yet`
- **拖到别处没有任何反应**：载荷只带一个私有 MIME 类型，掉在颜色名字框上也不会把 URL 塞进去（那会把 ASIN 键全污染）
- 每张卡片右上角还有个 `↑` 按钮 —— **和拖拽完全同一个动作**，触屏设备上这是唯一入口（HTML5 拖拽在触屏上基本不存在）

### 商品预告（`Coming Soon` / Teaser）

商品状态里还有第三种：**看得见、买不了**。编辑器里 `Visible on storefront` 下面新增
一个 `Coming Soon (Teaser)` 开关（在 Stock 上方，不用展开就能看到）。

打开后：

- **前台照常出现**（不像 `hidden` 那样消失），但：
  - 卡片角标**强制显示 Coming Soon**，覆盖原本的 New / Best-seller（单角标，不叠加）
  - 详情里颜色仍可点、可切变体图；**尺码全部置灰不可选**
  - 底部加购按钮变成禁用的 `Coming Soon`
- **购物车防御**：如果她在标记前已经加购，购物车会明确显示

- 关掉开关后：尺码解锁、加购恢复、角标回到原本的 `tag` 与 `badge_color`。

### 断货开关（`Stock` 网格）

编辑弹层底部（规格组下面）有一个**默认折叠**的 `Stock` 面板。标题右边直接显示当前状态，不用展开就知道有没有断货：

```
┌──────────────────────────────────────────────────┐
│  Stock   3 / 140 sold out                     ⌄  │
└──────────────────────────────────────────────────┘
```

展开后是一张「颜色 × 尺码」的格子表，**一个格子 = 一个可下单的组合**：

```
           S    M    L    XL
  Black    □    □    □    □
  Green    ■    ■    □    □     ← 点格子：只切这一个组合
  White    □    □    □    □
           ↑ 点列头切整列；点行头切整行
```

- **点格子**：切换这一个组合（`Green|S` ↔ 有货）
- **点颜色名 / 尺码名**：切换整行 / 整列 —— 这就是「Green 全断了」那个动作，内部写 N 个键
- **`All available`**：一键清空所有断货标记（没有标记时是灰的）
- 底部显示 `140 combinations`，让你确认格子数对不对
- 只有一个规格轴的商品（如只有颜色）显示成一排 chip，不画 1 × N 的表
- 还没加任何规格时提示 `Add a colour or a size above first`

**折叠的理由**：20 × 7 的商品是 140 个格子，而绝大多数编辑会话根本不碰库存。

**保存时才落库。** 网格改的是草稿，点 `Save changes` 才写 `products.sold_out_variants`。保存前会跑 `pruneSoldOut(draft.soldOut, { specs })`，把**已经不存在的组合**从清单里剔掉 —— 否则删掉 `Green` 之后，`Green|S` 会永远留在数组里，哪天再加回一个同名颜色就会莫名其妙地断货。

### 尺码的显示顺序（`XS → S → M → L → XL → XXL → 3XL`）

表格里的 `Size` 是按**你填写的顺序**存进数据库的 —— 不同的人填的表，顺序不一样，同一个颜色
尺码组可能是 `XXL, S, L, M, XL`。尺码是有大小关系的，乱着显示看的人要多读一遍，库存网格也不好扫。

所以**所有展示尺码的地方都会先排一遍序**，判据只有一个（`src/utils/sizes.js` 的 `sortSizes`）：

| 尺码 | 排成 |
| --- | --- |
| `XXL, S, L, M, XL` | `S, M, L, XL, XXL` |
| `XS, S, M, L, XL, XXL, 3XL` | 原样（本来就对） |
| `2, 12, 14, 6, 4, 8, 10` | `2, 4, 6, 8, 10, 12, 14`（**按数字大小**，不是按字符） |
| `160, 120, 150, 130, 140` | `120, 130, 140, 150, 160`（童装身高码同理） |
| `2XL` / `XXXL` / `Small` | 等同 `XXL` / `3XL` / `S`，插在正确的位置 |
| `One Size`、认真在输入的空白格 | 排在最后，并保持原来的先后 —— 不认识的不替人猜 |

生效的位置：

- **前台详情弹层**的尺码按钮
- **后台 Stock 网格**的列头（颜色 × 尺码那张表）
- **后台编辑器的 ASIN 列表**（`Light Blue / S` → `… / XXL`）
- **后台编辑器的选项输入框**：显示按大小排，但**正在输入的那一组不动**（否则敲一个字输入框就横跳），
  失焦后归位；下面会多一行小字 `Shown smallest → largest. The order you typed is what gets saved.`

两条**不变**：

1. **颜色不排序**，永远按商品自己的规格顺序（颜色没有大小，编辑器里调过序的就是你想要的顺序）。
2. **数据库里的 `specs` 数组一个字节都不改。** 排序只发生在渲染时 —— 历史选款码里有按「选项
   下标」解析的老版本，数组一挪，老码就指到别的尺码上了（而且不会报错）。所以你在编辑器里
   看到的整齐顺序，不会改变这条商品在库里存的顺序。

---

### 改颜色名（`藏青色` → `Navy`）会不会丢 ASIN？

`asins.variants` 的键是「颜色|尺码」这个**字符串**，不是颜色在规格里的位置。所以改名字必须连键
一起改，否则原来的 ASIN 全变成孤儿（面板一片 `Missing ASIN`），而新颜色看起来从来没配过。

编辑器现在会自己认这件事：

- **直接改名**（点开颜色输入框，把 `藏青色` 改成 `Navy`）：ASIN 面板当场把这些 ASIN 挪到
  `Navy / *` 名下，并出现一行黄色提示
  `Renamed 藏青色 → Navy — 5 ASINs follow the new name and are saved under it.`
  点保存，`products.specs` 和 `asins.variants` 一起改，ASIN 一个不少；断货标记
  （`sold_out_variants`，用的是同一个键）也跟着挪 —— 不会「改个名就自动补货」。
- **先删旧颜色、再加新颜色**：这是两件事，系统**不猜**。新颜色的每个尺码显示红色的
  `Missing ASIN` 占位符 + `new` 小标，等你填；旧颜色的 ASIN 也没有丢，它们留在面板下方的
  `Not in the options above any more` 区块里，一行一个 ✕，确认不要了再清。

| 你做的操作 | ASIN 去哪 | 面板上看到 |
| --- | --- | --- |
| 把一个颜色改名 | 全部挪到新名字下 | 黄色 `Renamed A → B — N ASINs …`，行立刻填好 |
| 改一个尺码名（`L` → `Large`） | 该尺码在每个颜色下都挪 | 同上 |
| 删掉旧颜色，再加一个同义的新颜色 | 不挪，新颜色空着 | 新行 `Missing ASIN`，旧 ASIN 在 extras 里 |
| 只改大小写（`navy` → `Navy`） | 不动库 | 没有提示（键本来就是大小写不敏感匹配） |
| 两个颜色互换名字 | 不动 | 没有提示（分不出哪个是"改名"） |

**怎么区分「改名」和「删掉再加」**：只有「旧名字在整个列表里都不见了，而且新名字原来没有过」
才算改名 —— 删一个加一个时，被顶掉的位置上会出现一个**原来就存在**的颜色，所以不算。
拿不准时宁可不动：猜错的代价是把 A 颜色的 ASIN 装到 B 颜色的订单上，没人在打包前会发现。
`npm run test:rename` 用 64 条断言钉着这个判断（含碰撞、大小写、只改尺码、只有一个颜色轴）。

唯一要接受的代价：**改名会让之前发出去的、按字面值存的选款码（v3/v4/v5）仍指向旧名字**。
码本身不会失效（id 还是那个 id），但那条码里的颜色名和现在的规格对不上。按位置存的 v1/v2 码
不受影响。已经发出去的码如果还在有效期，改名后建议让红人重新生成一次。

### 补图：不用离开后台就能打开亚马逊

主图 URL 输入框下面有一枚链接：

```
[↗] View on Amazon  Dark Blue / XXL
```

点开就是 `https://www.amazon.com/dp/{ASIN}`，新标签页打开，尾部灰色小字是**这个 ASIN 属于哪个
颜色/尺码**。补图的路线从「前台找链接 → 亚马逊 → 切回后台」变成「后台点一下 → 复制图片地址 → 粘回来」。

- 取的是**面板里第一行真的填了 ASIN 的**那一个：颜色按商品自己声明的顺序，尺码 `S → XXL`。
  不是「对象里第一个键」—— `asins.variants` 是 jsonb，键序是存储格式的副产物（HANDOVER §22.1）
- 一个可用 ASIN 都没有 → 这枚链接**不显示**；只有残缺的（不足 10 位、带空格、整条 URL、带引号）
  也不显示，因为 `dp/` 后面接空串会落到亚马逊首页，比没有链接更费时间
- 在右边 ASIN 面板里刚粘完就生效，**不用先保存**
- `target="_blank"` + `rel="noopener noreferrer"`：新标签页，且亚马逊看不到后台的 URL

### 分类筛选（搜索框右边）

搜索框旁边的 **Category** 下拉只显示**库里真的有商品的分类**（空分类不会出现，选了也不会
出来一片空白），第一项 `All (195)` 是不筛选。

```
[ 🔍 Search 货号 / ASIN / id — or paste a list ]  [ Category  Tops ⌄ ]  [ ⚠ View Sold Out ]
```

下拉里还有一个**伪选项** `⚡ Deal Items (12)`：秒杀状态是 `sale_start` / `sale_end` 现算的，
不是一列，所以 `categories` 表里永远不会有它。选中它，列表只剩「两端都填了、且还没结束」的
商品（进行中 + 排期中，已结束的不算）—— 这就是"今天要跟的活动"那一批。

配合批量搜索的流程：**先切到 `⚡ Deal Items` → `Select all` → 批量改角标 / 改置顶 / 挑出要
延期的**，不用再逐个复制货号贴进搜索框。数字按整本目录算，回答的是"点下去能看到多少件"。

三条规则：

1. **三个控件是「且」的关系**。选了 Tops 再搜一个货号，就是「Tops 里搜这个货号」；再点
   `View Sold Out` 就是「Tops 里、这个词命中的、有断货的」。任何一个不满足就不显示。
2. **「全选」只勾当前看到的**。筛选后点左上角 `Select all`，勾的是筛选剩下的那些，批量
   `Hide / Unhide / Delete / To top / To bottom` 也只作用在它们身上 —— 不会误删看不见的商品。
   已经勾上的商品切换分类后仍然保持勾选（`N selected` 不变），这样能跨分类攒一批一起处理。
3. **筛选期间拖拽是关的**（列表上方会写明原因）。拖动会重写整个 `sort_order`，只对完整目录
   安全；要调位置用 `⤒ ⤓` 按钮，它们在筛选时照常可用。

清空搜索词、把下拉拨回 `All`、关掉 `View Sold Out`，列表立刻回到完整目录（顺序就是你拖过的顺序）。

### 批量搜货号（从 Excel 直接粘）

从表格里复制一列货号，直接粘进搜索框就行：

```
P9B013
H4E311
G7N002
```
或者 `P9B013, H4E311, G7N002`、`P9B013;H4E311`、用空格隔开 —— 都对。

**分隔符**认这些：换行、空格、Tab、`,` `;`，以及中文输入法下的 `，` `；` `、`。
首尾空格会清掉，空片段（末尾多一个换行是常态）直接忽略，重复的货号按大小写不敏感去重。

**两种模式，边界很清楚：**

| 输入 | 模式 | 匹配规则 |
|---|---|---|
| 一个词 | 模糊（和以前一样） | id / 货号 / 名称 / 分类 / ASIN 里包含它就命中，所以 `P9B0` 能搜出一堆 |
| **两个及以上** | 批量 | **只按货号精确匹配**，任意一个命中就显示（OR），`P9B0` 这种前缀不再算 |

输入框下方会出现一行提示：

```
Bulk search mode: 10 SKUs · 8 matched
```

`4 SKUs` 是你粘了几个，`8 matched` 只在**少于**粘贴数时才出现 —— 少了两个通常意味着
表里有两个货号在库里不存在，这比"列表看着有点少"有用得多。一个都没命中时，空状态会直接
说「None of those 10 货号 matched a product.」

**和另外两个筛选器仍然是「且」**：粘 20 个货号 + 选 Tops，就是"这 20 个里的 Tops"。
批量模式下的 `Select all` 也只勾筛出来的这些 —— 于是「粘一列货号 → 全选 → 批量隐藏/删除」
就是一条可用的批处理路径。

> 实现上是一层 `Set`：粘 100 个货号 × 273 个商品是 273 次哈希查找，不是 27,000 次子串扫描
> （实测 300 商品 × 100 货号 < 1 ms）。解析函数 `parseBulkQuery` 是纯函数，`test:filter`
> 里 [8] [9] 两节钉着分隔符、去重、模式边界和顺序。
>
> 还有一个坑专门处理了：单行 `<input>` 在部分浏览器（Safari / 某些安卓输入法）粘贴多行时会
> **把换行直接删掉**，十个货号会粘成 `P9B013H4E311…` 一个大 token，批量模式静默失效。
> 所以带换行的粘贴由 `onPaste` 接管，换行统一换成空格再进状态；不含换行的粘贴交给浏览器，
> 光标行为不变。

### 角标颜色（Badge）

后台编辑器的 **Badge** 一行：左边填文字（`New` / `Best-seller`…），右边那个方块是颜色，
点开是系统调色板，下面 6 个圆点是常用色（Charcoal / Terracotta / Red / Amber / Green / Blue），
最右的 `Default` 回到默认的炭灰底。

```
Badge  optional
[ New            ]  [■]   ● ● ● ● ● ●   Default
```

- **颜色是内联 `style`，不是 Tailwind 类名** —— 任意 hex 都能用，也不会在打包时被摇掉
  （动态类名 `bg-[${color}]` 会因为"没在源码里出现过"被 purge，这正是当初的坑）。
- **文字颜色自动选**：按 WCAG 相对亮度比较米白和炭灰哪个对比度高，所以浅色底自动变深字，
  深色底自动变浅字，10px 的小角标也看得清。

#### 角标栈（左上角，最多两行）

黑五期间一件商品要同时说两件事：**「它是什么身份」**和**「便宜多少」**。所以角标不是
"一个位置二选一"，而是**最多两行**，全部收在图片左上角，纵向排列（卡片 6px、详情 8px）：

```
┌──────────────────┐
│ Black Friday     │  ← 第一行：身份
│ 40% OFF          │  ← 第二行：促销 / 强推
└──────────────────┘
```

**第一行（身份）**，按顺序取第一个成立的：

| 顺序 | 来源 | 例子 |
|---|---|---|
| 1 | 大促标（`sub_tag`） | `Black Friday` |
| 2 | 秒杀时间窗（`sale_*`） | `Limited Deal` |
| 3 | Coming Soon（`isTeaser`） | `Coming Soon` |
| 4 | 普通标（`tag`） | `NEW` / `Highly Recommend` |

**第二行**：有折扣放折扣（`40% OFF`），没有折扣放普通标。Coming Soon **独占一行** ——
一个买不了的款，"省 40%" 是没有意义的承诺。

#### 同一件商品，三个面三种说法

这是本版的重点：角标内容取决于**它被贴在哪里**，不是取决于商品本身。

| 面 | 第一行 | 第二行 | ACC |
|---|---|---|---|
| 常规货架（All / Tops…） | 大促 / Limited Deal / Coming Soon / 普通标 | **只放普通标** | 不显示 |
| ⚡ Deals 专区 | 大促 / 普通标（**不出现 Limited Deal**，**与本专区同名的大促标也不挂**） | 折扣 | 不显示 |
| 详情弹层 | 大促 / Limited Deal / Coming Soon / ACC / 普通标 | 折扣 / 普通标 | 显示 |

- **目录里为什么不出折扣**：货架上每一件都在被比较，一行 `40% OFF` 会把视线从
  "这是什么"拉到"多少钱"。价格要到专区里才有意义
- **专区里为什么不出 Limited Deal**：整个专区都在秒杀，再写一遍是零信息。所以专区的
  卡片第一行是大促标或强推标，第二行才是数字 —— 两件都没有时，数字自己占一行
- **专区里也不重复自己的名字**：进了 `🔥Black Friday` 专区，整屏都是黑五，每张卡再
  顶一枚 `Black Friday` 同样是零信息。判断走 `isSameCampaign`（忽略大小写、空格、
  emoji 和尾部的 `Deals`/`Sale`），所以 Tab 名 `🔥Black Friday` 与角标 `Black Friday`
  认得出是同一场活动。常规货架**不**去重 —— 那里的 `Black Friday` 正是商品的关键信息
- **详情页永远给全**：不跟着"从哪个 tab 点进来"变。卡片是"扫"，详情是"判断"
- **ACC 只在详情页**（见上一节）

#### 几条边界

- **Coming Soon 与秒杀同时存在时 Coming Soon 胜出**：一个买不了的款挂「限时秒杀」
  比挂「五折」更误导（点进去发现尺码全锁着）。大促标仍可覆盖它 —— 那是运营明确要
  传达的活动身份
- **两行封顶**：169px 宽的卡片放不下第三枚。第二行被折扣占着时，普通标让位
- **普通标看得见，只是矮一行**：正在秒杀的商品，常规目录第一行是 `Limited Deal`、
  普通标排在第二行；进了专区它反而升到第一行（`Limited Deal` 被摘掉）。所以批量弹窗里
  "排在第二行"从不等于"看不见"，只有 Coming Soon 独占一行才会把普通标挡掉
- 全部是**纯文字**：没有 `⚡` / `🔥` / `💰`
- 颜色规则没变：每个角标用自己的 `badge_color` / `sub_badge_color`，文字色按亮度自动选
  （`badgeStyle`），没设颜色就是默认炭灰
- 渲染逻辑只有一处：`utils/deal.js` 的 `badgeStackFor(product, now, { zone })`。
  `zone` 是 `'catalogue' | 'deals' | 'detail'`，卡片和详情都调它，所以三面不可能长歪

#### 快捷模板（Quick fill）

文字框下方一排彩色胶囊，**点一下同时填好文字和颜色**：

```
Quick fill  [New] [Best-seller] [Trending] [Must-have] [Restock] [Coming Soon]
```

| 胶囊 | 颜色 | 用途 |
| --- | --- | --- |
| `New` | 祖母绿 `#1F7A55` | 上新款 |
| `Best-seller` | 焦橙 `#B34E17` | 已验证爆款 |
| `Trending` | 潮流紫 `#7C3AED` | 当前热门趋势 |
| `Must-have` | 深藏青 `#1E2E4F` | 红人必入款 |
| `Restock` | 天蓝 `#2470AE` | 返场补货 |
| `Coming Soon` | 石墨 `#333333` | 商品预告（配合 Teaser 开关） |

- **胶囊就是预览**：它用和前台角标完全相同的内联样式画（底色 + 自动文字色），
  点下去长什么样，卡片上就是什么样。
- **填完还能改字，颜色不动** —— "Trending" 改成 "Trending Now"，紫色留着；这时胶囊会
  留下一圈浅描边，意思是"你现在这个颜色来自它"。
- **六个颜色全部过 WCAG AA（≥ 4.5:1）**，所以白色文字在上边读得清；焦橙/天蓝特意比日常
  认知里的"爱马仕橙 / 天蓝"深一档，鲜亮版只有 2.9–3.4:1，小字会糊。
- 再点另一个胶囊是**整体替换**（文字 + 颜色都换），不会和刚打的字粘成 "Trending NowRestock"。
- 颜色**不是**锁死的：模板只是起点，右边的调色板和 6 个圆点照常用。

**这一列是独立的数据库列 `badge_color`**，`supabase/07-badge-color.sql` 已于 2026-10-22 执行，
现在正常工作。换新环境 / 重建库时如果漏了这一步，表现是：

- 编辑器 Badge 下方会出一条琥珀色提示，明说「这个颜色存不进去，去跑 `supabase/07-badge-color.sql`」；
- 点保存时提示条会变成 `Saved, but the badge colour was not stored — …`，**不会**假装保存成功
  （文字本身照常保存）；
- 前台继续显示默认的炭灰角标。

原因：`productStore` 探测到列不存在时会把 `badge_color` 从**每一次写入**里剔掉 —— 否则整个
保存会 400，连商品都改不了。所以「能改商品」和「能存颜色」在这件事上是两件事，别把它们混为
一谈：颜色不生效先看列建了没有。

```sql
-- Supabase Dashboard → SQL Editor → 整段粘贴 → Run（幂等）
-- 文件：supabase/07-badge-color.sql
alter table public.products add column if not exists badge_color text;
```

### 排序（拖拽 + 快捷按钮）

**主路径是拖拽**：鼠标按住任意一行，上下拖到想要的位置，松手即生效。

- **按住整行拖动**，移动超过 **6px** 才算拖拽开始 —— 这个阈值是为了让「点击」仍然是点击
- 勾选框和右侧按钮**不参与拖拽**（它们自己 `stopPropagation`），点它们不会误触发拖动
- 拖动中的行会抬起（阴影 + 描边），其余行实时让位
- 松手后一次 RPC 写入，Toast 显示 `Moved to position N`
- **筛选 / 搜索状态下拖拽自动关闭**（列表上方会提示），因为排序是相对整个目录的，不是相对搜索结果
- 拖拽用的是 `@dnd-kit/core` + `@dnd-kit/sortable`（bundle +45.6 kB / gzip +15.8 kB）

每行右侧还保留四个图标，作为精确控制和筛选状态下的备用手段：

```
⤒  ↑  ↓  ⤓     ✎  🗑
│   └──┴──┘   │
│   一格一格  └─ 编辑 / 删除
└──── 直接到最前 / 最后
```

- **⤒ / ⤓（到最前 / 最后）**：只写**一条** update。置顶 = `min(sort_order) - 1`，置底 = `max + 1`，其余 194 行一个数字都不动
- **↑ / ↓**：交换相邻两行的 `sort_order`，两条 update
- 已经在最前 / 最后时，对应按钮自动禁用（不会写无效值）
- **窄屏（< 640px）只显示 ⤒ ⤓**：四个图标在手机宽度上会挤掉商品名，而单步移动在手机上本来也不好点

**拖拽为什么必须走 SQL 函数**

`sort_order` 是**密集**的（0…194，无空隙）。拖到第 3 位意味着要重写中间那 190 行的序号。前端循环发 190 条 update 没有事务包着 —— 断在第 90 条，数据库就停在一个「一半新一半旧」的顺序上，而且没人知道是哪一半。

所以拖拽调用 `reorder_products(p_ids text[])`（`supabase/06-reorder.sql`）：一条 `update ... from unnest(...) with ordinality`，**单语句、单事务**，195 行要么全对要么一行没动。函数要求传入**全量** id 数组（数量不等于全表行数就抛异常），这就是筛选时禁用拖拽的原因。

> 函数写的是 0…N-1 连续序号，所以拖一次会顺带**抹平**置顶/置底留下的负数和空洞。

**筛选状态下按钮仍然是对的**：行的位置用的是它在**整个目录**里的下标，不是当前筛选结果里的下标。所以「搜一个货号 → 点 ⤒」会真的把它送到全站第一位，而不是搜索结果的第一位。

**数值会漂移**（置顶几次之后出现 0, -1, -2…）。这无害：唯一的消费者是 `order by sort_order`，没有任何地方要求序号连续。跑一次拖拽就会重新压成 0…N-1。

**实时**：写入成功后本地缓存立即重排；其他标签页和前台靠 Realtime 在 180ms 防抖后整体重取，不需要手动刷新。一次拖拽会产生 195 条 UPDATE 事件，防抖把它们合成一次 refetch。`npm run smoke:realtime` 的 `[4]` 段验证这条链路。

### 缺货看板（View Sold Out）

筛选区右侧的红色按钮，是一个**跨分类**的视图：只显示「至少有一个变体断货」的商品。

- 每张卡片直接列出断货组合：`Sold out  Burgundy / XL ×  Red / S ×`（超过 4 个显示 `+N more`）
- 顶部横幅：`2 sold-out variants across 1 style`
- **Export Sold Out List**：复制纯文本，格式是给采购直接用的

```
Aoysky · sold out · 2026-10-21
1 style · 2 variants

P9B053  Striped Long Sleeve Shirts Open Tie Back Casual Pullover Tops
  Burgundy / XL          B0HBBPYKB9
  Red / S                B0HBBR65HH
```

- 右侧的下载图标存成 `sold-out-YYYY-MM-DD.txt`，内容一样
- **标签上的 × 就是「补货了，取消标记」**，按单个颜色/尺码取消。没有「整款一键恢复」——
  库存是一个尺码一个尺码回来的，一键恢复等于把不存在的货重新放出来
- 这个视图里**拖拽是关的**（排序 RPC 要求全量 id 数组），`⤒ ⤓` 照常可用

Realtime 重取 `categories` 表跟上。想确认当前顺序可以在控制台跑 `AOYSKY.categories()`。

#### 分类栏的鼠标操作（桌面端）

手机本来就能滑，桌面端只有触控板用户滑得动 —— 鼠标既没有横向滚轮，也不能按住拖。
分类一多，右边那几项就永远点不到。现在补上两种鼠标姿势（`hooks/useDragScroll.js`）：

| 操作 | 行为 |
|---|---|
| 鼠标停在栏上，滚轮上下 | 映射成**左右滚动** |
| 按住左键拖动 | 平移，和手机上滑一样 |
| 滚到最右/最左还继续滚 | **把事件还给页面**，sticky 栏不会锁死整页滚动 |
| 触控板横向手势 | 不接管（浏览器本来就会左右滚，再翻译一次等于双倍速） |
| 位移 < 5px 松手 | 仍然算点击；拖拽之后那一次 `click` 在捕获阶段被吃掉 |
| 触摸 / 手写笔 | 完全不拦（`pointerType !== 'mouse'` 直接返回），原生惯性保留 |

滚动条本来就用 `.no-scrollbar` 隐藏了，右边缘有一层渐隐提示还有内容；
键盘 Tab 到栏外的 chip 时浏览器会自己把它带进视野，所以隐藏滚动条不影响可达性。

数学部分（到边判断、行/页模式的折算、拖拽方向、5px 阈值）在
`utils/horizontalScroll.js`，纯函数，`test:scroll` 30 条覆盖；浏览器行为由
`smoke:gate [5ab]` 守。

- 外壳从 768px 放宽到 1680px（`Lookup` / `Developer` 页有各自的内层宽度，不受影响）

### 批量操作

搜索框下面一行是 `☐ Select all (139)`。勾上任意一个商品，右侧就出现批量操作条：

```
☑ Select all (195)   2 selected
  [ To top ] [ To bottom ] [ Hide ] [ Unhide ]
  [ Batch Edit Badge ] [ Batch Edit Deal ] [ Batch Edit Category ] [ Delete ]  ✕
```

- **每个商品行最左边有独立勾选框**，可以逐个挑
- `Select all` 勾的是**当前筛选结果**，不是全部商品 —— 先按分类筛到 Knitwear 再全选，就只动 Knitwear
- **To top / To bottom**：把选中的这几个整体送到最前 / 最后，**并保持它们之间的相对顺序**（选中 5 个，原来谁在谁前面，置顶后还是这个次序）。执行后**不清空选择**，因为接下来通常是继续 Hide 或编辑同一批
- **Hide**：批量下架，选中的全部打上 `hidden: true`
- **Unhide**：批量恢复上架
- **Batch Edit Badge**：给选中商品统一挂角标。弹窗问的不是"怎么改"，而是**"放哪一行"**
  —— 前台只有两行，两行各对应一个槽位（`badgeWriteFor`）：
  - **第二行 · 普通标**（默认）：写 `tag`，**不碰**已有的大促标。已有大促标/秒杀的
    商品它排在下面，没有的它就是第一行。可另勾「同时设置第一行的大促标」
  - **第一行 · 活动标**：写 `sub_tag`，替换原有的大促标（普通标不动）。秒杀派生的
    `Limited Deal` **压不住**它 —— 黑五统一挂 `Black Friday` 用这个。进了同名专区它会
    自动隐藏（整页都是这场活动）
  - 弹窗直接列出三种落位各有多少件：**显示在第一行 / 排在第二行 / 完全看不见**。
    数字跟着模式实时变（换到第一行，几乎每一件都是「第一行」），"点完到底看得见几件"
    在点之前就答完了
  - "排在第二行"是真的看得见（目录第二行、专区里还会升到第一行），所以不再谎报
    "被折扣挤掉"—— 只有 Coming Soon 独占一行才会把普通标挡掉
- **Batch Edit Deal**：统一原价 / 折后价 / 开始 / 结束日期，写五个 `sale_*` 列。日期补成
  整天的边界（`T00:00:00` → `T23:59:59`），`Next 7 days` 一键填本周窗口。`Pin` 留空 =
  **不动** `deal_priority`，所以"只把结束日推后一天"不会把早上钉好的商品全部取消置顶。
  `Clear deal` 是同一件事的反面：五个字段 + 置顶一起归零
- **Batch Edit Category**：下拉选已有分类或新建一个，两种语义并排显示各自动多少件：
  `Overwrite all`（全部搬过去）与 `Only fill uncategorised`（只补没分类的）。一个商品只有
  一个 `category` 列（FK 指向 `categories.name`），所以"追加"不可能是两个分类。新分类名
  先 `addCategory` 建行再写商品 —— 顺序反了会撞 FK
- **Delete**：批量彻底删除，**会先弹一个不可撤销的确认框**
- `✕`：清空选择（Hide / Unhide 执行后也会自动清空）

**彻底删除的警告**

```
⚠ Delete 12 products permanently?
彻底删除不可恢复，且绝对不能重排剩余商品的 id，否则历史码会失效！
Remaining products keep their current ids — codes issued before
today still resolve correctly.
Deleted 货号 are also removed from the ASIN table.
[ Cancel ]  [ Delete permanently ]
```

确认后做三件事：

1. 从商品库移除这些商品
2. **剩余商品的 id 一个都不动**，也不重新排序 —— 这是「历史码永远有效」的前提
3. 把这些货号对应的 ASIN 映射一起从 `asins.js` 里清掉，否则搜索和后台查询里会留着幽灵条目

> 新建商品时 `id` 取**现有最大编号 + 1**，不是「第一个空位」。删掉 `p003` 之后新建的仍然是 `p004`，绝不会把 `p003` 这个号发出去 —— 万一某个旧码里还留着 `p003`，复用编号会让它指向另一个商品，而且**静默指错**。

**图片 URL 存在哪**

保存时 `variantImages` 和商品一起写进 `products.variant_images`（`store/mapping.js` 里的字段白名单必须带上它，漏了就静默丢字段 —— 这是本项目反复出现的一类 bug，`npm run test:mapping` 专门盯它）。分类清单在 `categories` 表。前台所有组件都从 store 读，写入成功后本地缓存立即更新，所以保存后不用手动刷新；**其他人**通过 Realtime 在几秒内跟上。

**把编辑结果固化进仓库**（可选，用来做版本备份）

线上已经是 Supabase 为准，所以这一步不是必须的。它的价值是：商品数据有 git 历史、能回滚、换 Supabase 项目时能一键重灌。

1. 在编辑器里调好商品
2. 点 **Copy as products.js**（或 Export JSON 下载）
3. 粘贴覆盖 `src/data/products.js` 里对应的部分
4. 提交代码

**Copy as products.js 到底复制了什么** —— 两个导出，顺序固定：

```js
/* Paste this over the matching block in src/data/products.js */

export const categories = ["Tops", "Knitwear", "Bottoms", "Uncategorised"]

export const products = [
  {
    id: "p001",
    sku: "P9B013",
    name: "P9B013",
    category: "Tops",
    image: "./placeholders/placeholder.svg",
    specs: { Colour: ["Black", "Army Green"], Size: ["S", "M"] },
    variantImages: { Colour: { Black: "https://…/black.jpg" } },
    hidden: true,
    tag: "",
  },
  // …
]
```

- **`categories` 在最前面**，是你在分类面板里维护过的那份清单，按面板里的顺序导出 —— 粘回去之后栏目顺序不会变
- **`products` 里带 `hidden: true`**：隐藏状态就是普通字段，跟着一起导出。只有明确下架的商品才有这个键，在售商品不写，导出的 diff 干净
- `variantImages` / `hidden` / `sku` 都是**有值才出现**，空字符串的 `tag` 会一起带出来，粘回去不影响运行

另外还有一个 **Copy as asins.js** 按钮，导出当前的 ASIN 变体表（`{ 货号: { '颜色|尺寸': ASIN } }`）。批量删过商品之后可以用它把清理结果固化到 `src/data/asins.js`。

这样商品数据就进了版本库，不再依赖某个人的浏览器。

### 删除与安全（三个护盾）

后台是全站的写入口，这三层保护挡住的是「一次手滑就不可逆」：

- **单个删除要过弹窗**：点行尾垃圾桶不会直接删。弹窗写清
  `Are you sure you want to delete 货号 (商品名)? This action cannot be undone.`，
  只有红色 `Delete` 才写库；`Cancel`、点遮罩、按 Esc 都只是关窗。
- **批量删除 30% 熔断**：勾选数**严格超过**全目录 30% 时，弹窗变成红框警告，
  确认按钮在手动输入大写 `DELETE` 之前保持禁用。小批量仍是一键确认。
- **闲置 480 分钟（8 小时）自动登出**：后台连续 8 小时没有点击 / 滚动 / 键盘输入
  （`mousemove` 不算），先弹一条 `Session expired due to inactivity`，再
  `signOut()`，登录门禁自动回来。任何真实操作都会重置计时。

判断逻辑在 `src/utils/adminSecurity.js`（`computeBulkDeleteGuard` /
`readIdleTimeoutMs`），超时 hook 在 `src/hooks/useSessionTimeout.js`。

## 七、批量导入（货号 / ASIN / 颜色 / 尺寸）

把表格一次性变成商品库，不用一个个手录。

### 表格长什么样

四列，顺序随意，按表头名识别（`货号` / `SKU` / `item code` / `款号`，`ASIN` / `ASINs`，`颜色` / `Colour` / `Color`，`尺寸` / `Size` / `尺码`）：

| 货号 | ASIN | 颜色 | 尺寸 |
|---|---|---|---|
| AMZ-1003 | B0C1234ABC | Black | S |
| AMZ-1003 | B0C5678DEF | Black | M |
| AMZ-1003 | B0C90AB1CD | White | S |
| AMZ-1005 | B0C9999XYZ | Oatmeal | M |
| AMZ-1012 | | White | |

- **一行一个变体**（一个货号 + 一个颜色 + 一个尺寸 + 一个 ASIN），这是推荐写法，也是亚马逊后台导出表本来的样子。导入时加 `--merge-rows`
- 同一个货号的多行会合并成一个商品，每行的「颜色 + 尺寸」各自记住自己的 ASIN
- 颜色/尺寸多值用逗号分隔；尺寸也认 `/`（`S/M/L`），颜色**不认** `/`（`Cream/Tan` 是一个颜色）
- 尺寸列留空 → 该商品**整个不生成 `Size`**，前台按 one size 处理
- **颜色**去重后保留首次出现顺序，不排序（`Black, Brown, White` 读起来就挺好）
- **尺寸**去重后按常规顺序排：`XS → S → M → L → XL → XXL → 3XL`，纯数字码按数值排（`120 → 160`），认不出的排最后
- **尺寸写法统一**：`2XL` 和 `XXL`、`XXXL` 和 `3XL` 视为同一尺码，统一成前者（表格是分批填的，两批写法不一致，不统一的话同一个商品会出现两个一样的尺码）
- **同一个「颜色 + 尺寸」出现两次** → 取第一个 ASIN，丢弃后面的，并在报告里列出来。亚马逊同一款重复上架时会出现这种情况，规则是「先到先得」

> 想保留表格原样：加 `--no-sort-sizes`（不排序）或 `--keep-size-spellings`（不统一写法）。

输入支持 `.csv` / `.tsv` / `.json`。`.xlsx` 请先在 Excel 里「另存为 CSV UTF-8」。模板见 `scripts/sample-sheet.csv`。

### 跑一条命令

```bash
npm run catalog -- 表格.csv
npm run catalog -- 表格.csv --dry-run     # 只看报告，不写文件
```

产出三个文件：

| 文件 | 内容 |
|---|---|
| `src/data/products.js` | 一个货号一个商品，`id` 为 `p001…`，`sku` 存货号原文 |
| `src/data/asins.js` | `{ 'AMZ-1003': { 'Black|S': 'B0C1234ABC', … } }` |
| `scripts/out/import.js` | 浏览器控制台脚本（旧方案，云端版本用 `npm run push` 代替；生成在 `scripts/out/` 而不是 `public/`，因为它含全量 ASIN，不能对外服务） |

### 规则

- **货号重复 → 直接停下报错**，列出重复的货号和行数，不合并、不加后缀。修好表再跑，或加 `--merge-rows` 显式合并（颜色/尺码取并集，ASIN 拼接去重）
  - 如果表格是**一行一个 ASIN 变体**（同一个货号多行，每行一个 ASIN），重复是正常的，直接加 `--merge-rows`
- **`id` 复用**：重复导入时同一个货号沿用上次的 `id`，所以重新导入不会让已发出的选款码失效
- **保留你的编辑**：重复导入时 `name` / `category` / `image` / `tag` 保留后台改过的值，颜色和尺码以表格为准。加 `--fresh` 才全部重置
- **ASIN 按变体存**：`asins.js` 是 `{ 货号: { '颜色|尺寸': ASIN } }`，后台查询直接显示红人选的「颜色 + 尺寸」对应的那一个 ASIN；组合不存在就显示「No matching ASIN」
- **后台彻底删除商品会连带清掉它的 ASIN 映射**（`asins` 表里同一事务删掉），所以删完不会在搜索和查询里留幽灵条目。重新导入表格会补回来；想把当前映射导成文件，用后台的 **Copy as asins.js**

### 合并的副作用

前台的颜色和尺码仍是**两张独立清单**，所以红人可以选出表格里并不存在的搭配（比如只有 `Black/M` 和 `White/L`，前台却允许 `Black/L`）。这是"规格组互相独立"这个模型本身的限制。

现在这种搭配不会再悄悄给错 ASIN 了 —— 变体表里查不到就显示「No matching ASIN」，运营一眼能看出这个组合没上架。如果要求前台就不允许选，得把同款按颜色拆成独立商品。

### 增量追加 ASIN（不重建商品库）

上面那条链路是**重建**：`npm run catalog` 重新生成 `src/data/products.js`，`npm run push` 再把整行商品 upsert 上去 —— 包括 `name` / `category` / `image`。第一次导入没问题；等运营已经在 `/#/admin` 里手工填了几周名字和图片，再跑一次就等于把它们全冲掉。

日常补货号走这条：

```bash
# 先看计划，一个字节都不写
node scripts/import-asins.mjs ~/Desktop/新一批.xlsx --dry-run

# 确认无误再真正落库
node scripts/import-asins.mjs ~/Desktop/新一批.xlsx
```

表格就是 `.xlsx`，第一个 sheet，表头 `货号 | ASIN | 颜色 | 尺寸`（按列序读，表头只用来提示）。**一行一个变体、一格一个值** —— 和上面那条链路的 CSV 不一样，这里不认逗号分隔的多值。

**它只做加法，是代码结构上的加法，不是承诺：**

| 表 | 写入方式 |
|---|---|
| `asins` | 按 `sku` 读出整张 `variants`，逐键合并后整行 upsert。表里没提到的键**根本不在 payload 里**，所以删不掉 |
| `products`（已存在） | update 的 payload 字面上只有 `{ specs }` —— `name` / `category` / `image` / `sort_order` 物理上不可能被覆盖 |
| `products`（新货号） | insert，`id` 从 `max+1` 发，`name` = 货号，`category` = `Uncategorised`，跑完调 `sync_product_id_seq()` 对齐序列 |

**它不会做的事**（每一条都是踩过或差点踩的坑）：

- 不删商品、不删变体、不删 ASIN
- **不重排、不删除 `specs` 里的选项，也不给已有商品新增规格维度。** 选款码存的是选项**下标**，`specTypes = Object.keys(specs)` 决定一个码有几位。给一个 one size 商品补上 `Size: []`，会让它历史上发出去的每个码都错位
- 不动已有商品的 `sort_order` —— 老码里还存着商品在列表中的位置

**写法对齐以线上为准**：脚本先读所有商品的 `specs`，把表里的颜色/尺寸按「完全一致 → 忽略大小写 → 忽略空格与 `&`/`-`」三档映射到线上已有写法，映射不上的一律原样新增并在报告里列出来。`2XL` 会被别名成 `XXL`（线上一直是 `XXL`/`3XL`/`4XL` 这套写法），`Navy` 会被别名成 `Navy Blue`。想加更多别名，改 `scripts/asins-import-core.mjs` 里的 `VALUE_ALIASES` —— 一张扁平表，颜色和尺寸共用。**别名必须在导入前加**：导完再改就得同时动 `products.specs` 和 `asins.variants` 的键，等于手工重构一次数据。

**同一个「货号+颜色+尺寸」两个 ASIN** 时脚本不猜，默认取先出现的那行，并把整组冲突打印出来。改判用 `--conflict=last` 或 `--conflict=skip`（skip = 两边都不写，保留线上原值）。

| 参数 | 作用 |
|---|---|
| `--dry-run` / `-n` | 只打印计划 |
| `--conflict=first\|last\|skip` | 同键冲突怎么处理，默认 `first` |
| `--only=asins` / `--only=products` | 只写一张表 |
| `--no-alias` | 关掉全部别名（`2XL`、`Navy` 都当成新取值） |
| `--sheet=Sheet2` | 读第二个 sheet |
| `--json=路径` | 聚合 JSON 写到哪，默认 `scripts/out/asins-import.json` |

无论 dry-run 与否，都会把 `{ 货号: { "颜色|尺寸": "ASIN" } }` 写到 `scripts/out/asins-import.json`（`scripts/out/` 已 gitignore），方便直接核对。

跑完会自动验收并打印结果：已有商品的 `name`/`image`/`category` 有没有被动过、原有变体有没有丢、表里每个键是不是都真的落库且 ASIN 一致、`specs` 键序有没有变。任一条 ✗ 就说明有问题。

> `.xlsx` 解析用 `xlsx`（SheetJS），只装在 `devDependencies` 里，只被这一个脚本引用，不会进前端包。想零依赖的话，把表另存成 CSV 也行 —— 脚本读的是第一个 sheet 的二维数组。

### 换季批量上新：先藏起来再补图

上面的 `import:asins` 是增量导入的底层入口；换季那种「一次几十个新货号、图片要补好几天」的场景，用 `batch:upsert` 更顺手，它可以**把新商品先藏起来**：

```bash
npm run batch:upsert -- "D:/Desktop/spring.xlsx"                      # 干跑，只打印计划
npm run batch:upsert -- "D:/Desktop/spring.xlsx" --write --hide-new   # 真写，新货号全部 hidden
```

`--hide-new`（别名 `--draft`）只作用于**本次新建**的商品：它们以 `hidden = true` 落库，前台立刻看不到（前台列表就是 `products.filter(p => !p.hidden)`）。补完名字、分类、图片后，去 `/#/admin/products` 勾选它们 → **Unhide** 上线。

**已经在卖的老货号不会被它藏起来**，这一点是结构性的：已存在货号的 update payload 字面上只有 `{ specs }`，`hidden` 连字段都不在里面；`hidden` 只在 `planProducts()` 的新建分支被赋值。

跑完会读回来自证两条：`✓ 已有商品的名字、图片、分类、可见状态、排序一个都没动` 和 `✓ 新建的 N 个商品都是隐藏的，前台看不到`。干跑阶段也会先告诉你 `可见性 · hidden = true —— 前台看不到`；没加 `--hide-new` 但有新建时，会多一行 `⚠ 还没补图就先上架了？`。

| 参数 | 作用 |
|---|---|
| `--write` | 真的落库（默认干跑） |
| `--hide-new` / `--draft` | 新建的商品 `hidden = true` |
| `--conflict=first\|last\|skip` | 同键冲突怎么处理，默认 `first` |
| `--no-alias` | 关掉 `2XL→XXL` / `navy→Navy Blue` 别名 |
| `--sheet=Sheet2` | 读第二个 sheet |

> `import:asins` **没有**这个开关，行为保持不变 —— 它是全量镜像链路的增量入口，藏不藏由运营决定，不该由一次导入顺手决定。

### 网页端批量导入：不开终端，在浏览器里传表格

换季上新不想开终端？`/#/admin/products` 顶部 **Add** 旁边就是 **Import (CSV/XLSX)**：

```
选文件 → 预览四个数字 → 确认导入 → 落库
```

表头和终端版一样：**货号 | ASIN | 颜色 | 尺寸**，一行一个变体。规则也照搬那一套，因为是**同一份代码**——`src/utils/asinsImportCore.js` 同时被 CLI 和浏览器引用，`scripts/asins-import-core.mjs` 现在只是个 re-export 壳子。合并逻辑不存在第二份实现，也就不存在第二处会 drift 的地方。

**预览弹窗的四个数字**（点确认之前一个字节都不写）：

| | 含义 |
|---|---|
| 🟢 全新货号 N 个 | 将被创建，**默认隐藏**（可勾掉） |
| 🟡 已有货号 N 个 | 只追加颜色/尺码与 ASIN，其它属性一律不动 |
| 🔴 严重格式错误 N 行 | 只有缺货号/颜色/尺寸、根本建不出变体的行才报错，并列出行号 |
| ⚠️ 缺少 ASIN N 行 | 变体照常建立，稍后去编辑器补 |

**缺 ASIN 不再丢行** —— 这是网页版和终端版唯一的行为差异。终端版会拒绝 ASIN 为空的行，但实际拿到的表常常是「颜色尺码齐了、ASIN 还在抄」，为了一列等明天的数据重跑整场导入不值得。所以只要货号/颜色/尺寸三列完整就导入，ASIN 面板里那一行显示 Missing，回编辑器补即可。

顺带几条：

- **货号大小写/空格不一致会按库中写法合并**：表里写 `g7f906`，落的是 `G7F906` 那个商品，不会建出第二个
- **ASIN 格式不对**（不是 10 位字母数字）不丢行：该 ASIN 跳过，变体照常建
- **同一变体给了两个不同 ASIN**：保留表中先出现的那个，并在预览里说明
- **新建货号默认 `hidden = true`**，前台看不到；已有货号的状态永不动（`hidden` 只在新行分支被赋值）
- 已有货号的 update payload 字面上只有 `{ specs }`——走的是 `updateProductSpecs()`，一个只写 `specs` 列的窄写入函数，想覆盖 name/image/category/badge/hidden 都没有那条路
- `.csv` 按 UTF-8 读，认不出表头再按 GBK 读一次（Excel 在中文 Windows 上导出的是 GBK）
- `xlsx`（SheetJS）用**动态 import** 懒加载，只有真选了文件才拉那个 429 kB 的分包，后台主包不受影响

### 首次导入的占位值

`name` = 货号、`category` = `Uncategorised`、`image` = 占位图、`tag` = 空。脚本跑完会把待补的货号列出来，去 `/#/admin/products` 逐个补名字、分类和图片。

### import.js 怎么用（已废弃）

`scripts/out/import.js` 是 localStorage 时代的产物：把数据写进浏览器的 `mako_products_v1` / `mako_asins_v1`。**现在的 store 已经不读这两个 key 了，所以它不再有任何效果。**

要往线上灌数据，用：

```bash
npm run push -- --dry-run    # 先看
npm run push                 # 真写
```

真要一次性手改，直接在 Supabase SQL Editor 里写，或者用后台编辑器改。保留这个文件只是因为它还被 `npm run catalog` 生成，删掉不影响运行。

> 它以前生成在 `public/import.js`，而 `public/*` 会原样拷进 `dist/` —— 等于把 4509 个 ASIN 放在一个公开 URL 上。现在改到 `scripts/out/`，`dist/` 里查不到任何 ASIN。

## 八、选款码机制

格式：`{CODE_PREFIX}-` + 明文 base62 载荷 → `aoysky-` + `7.luna.…`

> **前缀就是品牌简称。** 上线第二个品牌（B 品牌）时改 `src/utils/code.js` 里的
> **`CODE_PREFIX`** 一个常量即可（例如 `'ngb'`），所有新生成的码、后台输入框的占位符、
> 开发工具的示例、CLI 提示会一起跟着变。
>
> **为什么前缀必须是品牌名：** 两个品牌各有自己的 Supabase 与 catalogue，但商品 id
> 是各自编号的 —— B 品牌的 `p034` 和 A 品牌的 `p034` 是两件不同的衣服。把 B 的码粘进
> A 的后台，`decodeCode` 会直接返回 `Invalid brand prefix` 并**拒绝解析**；强行解析出来的
> 是一份名字、货号、颜色俱全却完全错误的订单，比报错贵得多。
>
> **历史老码不会失效。** `LEGACY_CODE_PREFIXES = ['zby']` 里的前缀仍然照常解析，
> 只有**发出**新码才用 `CODE_PREFIX`。 `MAKO-` 这种既非当前品牌也不在白名单里的前缀，
> 与外品牌一视同仁地被拒。
>
> 前缀比较大小写无关（`aoysky-` 和 `AOYSKY-` 都收），因为它可能被聊天软件改过大小写；
> 载荷是 base62、**区分大小写**，不能整体转大写。`scripts/test-code.mjs` 的
> `[5b]/[5c]/[5d]` 盯着这三条。

载荷用 `.` 分段（v7，8 段）：

```
7.{ref}.{ids}.{radix}.{specs}.{qty}.{ts}.{fp}
```

| 段 | 含义 | 编码 |
|---|---|---|
| `7` | 版本号 | v1–v6 仍可解码，见下 |
| `ref` | 红人标识 | 小写字母数字，最长 12 位 |
| `ids` | 选了哪些商品 | 数字部分（去掉 `p`）转 base62，首字母是模式：`r` 区间、`b` 位图、`s` 显式序列（有重复款时）、`t` 字面 id。紧跟一位是 `id` 数字部分的**补零宽度**（`p001` → `3`，不补零 → `0`） |
| `radix` | 选项打包用的进制 | 1 + 本码里最大的「颜色数 × 尺码数」，base62 |
| `specs` | 每行的选项 | 一行一位数字，表示它在该商品自己那张「颜色 × 尺码」网格里的序号；整列按 `radix` 压成**一个大整数**，base62。`_` = 全 0 |
| `qty` | 每款数量 | 全是 1 件时写 `_`；否则只写不是 1 的行：`行号:数量`，逗号分隔，都按 base62 |
| `ts` | 生成时间 | 秒级时间戳，base62 |
| `fp` | 选项指纹 | 4 位，见「改了颜色怎么办」 |

### v7 只装 4 件事：id、选项序号、数量、时间

名称、货号、ASIN **都不进码**，解码时按 `id` 去数据库实时查。

好处不只是短：

- 改名、改货号、改 ASIN 映射，**已经发出去的码立刻跟着变**，不用重发
- 商品被删了也不会整码失败 —— 那一行显示 `已下架商品（p001）` 并保留数量，其余照常

### 实例

红人 luna，4 款共 7 件（真实目录）：

```
code   aoysky-7.luna.r31,8,O,g.14.88v.0:2,2:3.1xK8rd.zQ4I    51 字符
       └┬┘ └──┬──┘└────┬────┘└┬┘└─┬─┘└────┬────┘└──┬──┘└─┬─┘
       前缀  版本+标识   id 区间 进制 打包选项  数量   时间  指纹
```

| # | 货号 | 颜色 / 尺寸 | ASIN | 数量 |
|---|---|---|---|---|
| 1 | P9B013 | Black / XS | B0H6XHHZ8N | 2 |
| 2 | P9B050 | Navy Blue / S | B0HD5PXG9K | 1 |
| 3 | H4E384 | Green / L | B0HB95DG7Y | 3 |
| 4 | N7W119 | Khaki / L | B0H8NXVXZC | 1 |

同一份选择在 v3 里是 209 字符，在 v4 里是 108 字符，现在是 **47**。

真实目录上的典型长度（线上 270 个在售商品）：

| 款数 | v6（旧） | v7 | 省下 |
|---|---|---|---|
| 4 | ~100 | **47** | 55% |
| 50 | 1004 | **138** | 86% |
| 70 | 1414 | **157** | 89% |

50 款的完整码长这样（可直接复制）：

```
aoysky-7.luna.r31,3-F,H-Q,S-Y,e-i,k-l,n,p-r,1J,1Q,1d,27,2B,3W,40,4b.1d.5C0lmu04mUvfcx5FCSZvI0rYykGNCJqeHH1ltB0K1uGXzEvln4KdWgQF._.1xK8qk.uPeA
```

`ids` 段选哪种模式由**长度**决定，编码器两种都算一遍取短的：连续号段用区间（`r`），
挑得散用位图（`b`，一个 bit 一个商品）。上面这 50 款是挑散的，区间仍然更短；
`脚本里 40 选 28、间隔 4` 这种就会自动走位图。

### 同一个商品多个变体

红人可以给同一款同时加购 `Black / M` 和 `White / L`。这时 id 会重复，区间/位图都表达不了，
`ids` 段改用 `s`（显式序列），一个 id 配一组选项，**不合并、不覆盖**：

| # | 货号 | 颜色 / 尺寸 | ASIN | 数量 |
|---|---|---|---|---|
| 1 | P9B013 | Black / M | B0H6XHHZ8N | 1 |
| 2 | P9B013 | White / L | B0H6XHYQ41 | 2 |
| 3 | P9B050 | Navy / S | B0HD5PXG9K | 1 |

规则：

- **编码器永远发 v7**，不再按长度挑 v4/v5/v6 —— 只有一套写入逻辑，老码只读不写。
- **顺序是"目录顺序 + 加购顺序"**：`r`/`b` 模式按 id 升序排（规格、数量跟着一起重排），
  `s` 模式保持红人加购的先后，所以后台看到的顺序和红人点击的顺序一致。
- 规格先按商品当前的 `specs` 清洗。**颜色被后台删掉的那一行直接丢弃，不会被编码成"另一个变体"** —— `{Colour:'Charcoal', Size:'M'}` 清洗后只剩 `{Size:'M'}`，那是另一个组合，不是红人选的。

### 改了颜色怎么办（v7 唯一的代价）

v7 存的是**选项序号**，不是 `Black` 这个字面值 —— 这正是 1000 字符变 138 的原因。代价是：
发码之后如果运营改了某款的颜色/尺码列表，序号可能指向别的组合。

所以码尾有 4 位**指纹**（选中商品各自的选项列表做 FNV-1a）。解码时重算一次：

- 一致 → 正常显示
- 不一致 → 后台弹黄条「颜色/尺码列表已变更，请核对这几行」，列表里那一行再加一枚
  `请核对颜色尺码` 标签
- 序号直接**越界**（选项被删少了）→ 该行不猜颜色，只显示商品名 + 数量，并标 `请核对颜色尺码`

关键点：**只有那一行受影响**。因为进制 `radix` 是整码共用的、也存在码里，一行解不出来
不会让后面所有行跟着错位（这正是把 radix 单独存一段的原因）。

### 为什么存 id 而不是数组位置

v1/v2 存的是"第几件"，调顺序或删商品后老码会指向错的商品 —— 而且是**静默指错**，最危险的那种。v3 起存 `id`，调顺序、删商品都不影响解码；真找不到就明确标成"已下架"，不整码失败。

### 兼容旧码

| 版本 | 载荷 | 处理 |
|---|---|---|
| v1 | `1.ref.mask.specs.ts` | 按位置解析，数量默认 1，返回 `legacy: true` |
| v2 | `2.ref.mask.specs.qty.ts` | 按位置解析，返回 `legacy: true` |
| v3 | `3.ref.ids.specs.qty.names.ts` | 按 id 解析，名称快照忽略（优先用目录里的当前名称），`legacy: false` |
| v4 | `4.ref.ids.specs.qty.ts` | 按 id 解析，字面值（base64），`legacy: false` |
| v5 | 同 v4 | `ids` 允许重复，`legacy: false` |
| v6 | `6.ref.ids.dict.refs.qty.ts` | 值字典 + 行索引，`legacy: false` |
| v7 | 见上 | 序号打包 + 指纹，`legacy: false`，**唯一还会写入的格式** |

v1–v6 至今仍能解（`decodeIdBased` / `decodeDictionary` / `decodeLegacy` 原样保留），
但它们只读不写：新生成的码一律是 v7。判定方式是「载荷里有没有 `.`」—— base64 不可能
出现点号，所以一个字符就能区分新旧信封。

`legacy: true` 时后台会显示黄色提示："这是旧版码，按位置匹配，商品列表可能已经变过"。位掩码超出现有商品数量的部分会单独列成"未知商品（原第 N 位）"，不会静默丢弃。

早期 v4 的规格写成 `Colour=Black,Size=M` 也能读 —— 解码时看到 `=` 就按显式键值对处理，否则按位置对应。

**为什么不做 6 位短码**

选款码必须能在**另一台设备**上解码 —— 红人用手机生成，运营用电脑查询，中间没有服务器，localStorage 也不跨浏览器。所以款式、规格、数量、时间必须全部编码进代码本身。

想要 `aoysky-XXXXXX` 这种短码，必须有后端存映射表，见第十一节。

```js
AOYSKY.decode('aoysky-My5sdW5hLnAwMDF-cDAwNi5Db2xvdXI9Q2hhcmNvYWwsU2l6ZT1MfkNvbG91cj1CbGFjayxTaXplPTM4LjIxLldvb2wtQmxlbmQlMjBXaWRlLUxlZyUyMFRyb3VzZXJzfkxlYXRoZXIlMjBQZW5ueSUyMExvYWZlcnMudG43NnFj')

AOYSKY.products()
```

### 2. 命令行（服务端 / 脚本）

```bash
node scripts/decode.mjs aoysky-xxxxx         # 人读格式
node scripts/decode.mjs aoysky-xxxxx --table # 表格
node scripts/decode.mjs aoysky-xxxxx --json  # 原始 JSON，可管道
node scripts/decode.mjs aoysky-xxxxx --csv   # CSV 到 stdout
```

退出码：`0` 成功，`1` 码无效，`2` 缺参数。

```bash

```

### 3. 后台 Developer 页（`/#/admin/developer`）

粘贴代码 → 格式化 JSON → 一键复制或下载 `selection_<ref>.json`。

### 返回的数据结构

```jsonc
{
  "ok": true,
  "version": 4,
  "legacy": false,                                 // true = v1/v2，按位置解析
  "ref": "luna",
  "createdAtMs": 1760946199000,
  "createdAt": "2026-10-20T07:23:19.000Z",
  "totalStyles": 2,
  "totalUnits": 3,
  "missing": [],                                   // 找不到的 id
  "warnings": [],                                  // 给后台显示的提示
  "items": [
    {
      "index": 0,                                  // 在选款码里的顺序
      "catalogueIndex": 0,                         // 在商品库里的位置，找不到时为 -1
      "id": "p001",
      "sku": "P9B013",                             // 货号，找不到商品时为空
      "asin": "B0H6XHHZ8N",                        // 按「货号 + 颜色 + 尺寸」查，查不到为空串
      "name": "Wool-Blend Wide-Leg Trousers",
      "category": "Bottoms",
      "image": "./placeholders/p001.svg",
      "qty": 2,
      "specs": { "Colour": "Black", "Size": "S" },
      "specText": "Black / S",
      "found": true,
      "missing": false                             // true = 已下架/未知商品
    }
  ]
}
```

解码失败返回 `{ ok: false, error: "..." }`，不抛异常。**商品被删不会导致整码失败**：那一条 `missing: true`、`found: false`，`id`、`qty`、`specs` 的值都保留（键名退化成 `Option 1` / `Option 2`，因为类型名不存进码），名称显示为 `Removed product (p001)`，仍计入 `totalStyles` / `totalUnits`。

### 在你自己的项目里调用

`src/utils/code.js` 是纯函数，不依赖 React：

```js
import { decodeCode, generateCode } from './src/utils/code.js'

const order = decodeCode(codeFromCreator)
if (!order.ok) throw new Error(order.error)

for (const line of order.items) {
  if (line.missing) console.warn('已下架：', line.id, line.name)
  console.log(line.sku, line.id, line.qty, line.specText, line.asin || '—')
}
```

**注意**：解码要把 id 还原成商品，读的是当前商品库。浏览器里读的是 `productStore` 的内存缓存（启动时从云端拉的那一份），Node 里读 `data/products.js`。货号和 ASIN 同理，来自商品库和 `asins` 表 / `data/asins.js`。

**两边会不一致，这一点必须知道**：CLI 读的是仓库里的 `data/*.js`，如果商品是在后台改的、没有回写文件，CLI 就会按旧数据解析。要么改完用 **Copy as products.js** 回写，要么直接用浏览器控制台的 `AOYSKY.decode()`（它读的是云端最新数据）。

## 十一、Supabase 数据层

这一节是整套协作能力的地基。出问题时九成的原因在这里。

### SQL 脚本执行顺序

全部在 Supabase → SQL Editor 里按顺序跑，**每个脚本都可以重复跑**（`create or replace` / `if not exists`）：

| 顺序 | 脚本 | 作用 | 不跑会怎样 |
|---|---|---|---|
| 1 | `01-schema.sql` | 建表 + RLS + Realtime + 序列 | 什么都没有 |
| 2 | `02-import-helpers.sql` | 导入后同步 id 序列 | 手动插入时 id 撞车 |
| 3 | `03-harden-asins.sql` | 收紧 `asins` 读取权限 | 匿名能读全部 ASIN |
| 4 | `04-product-links.sql` | 只读视图，给前台拼亚马逊链接 | 卡片上显示 `Listing not linked yet`，**不报错** |
| 5 | `05-sold-out.sql` | `products.sold_out_variants`（单变体断货） | 断货功能整体失效：前台全部视为有货，编辑器网格保存不上 |
| 6 | `06-reorder.sql` | `reorder_products(text[])`（拖拽排序的原子写入） | 拖拽松手后报 `PGRST202`，商品顺序不动；`⤒ ⤓` 按钮仍然可用 |
| 7 | `07-badge-color.sql` | `products.badge_color`（角标自选色） | 颜色选择器照常显示但存不住，编辑器出琥珀色提示 |
| 8 | `08-teaser.sql` | `products.is_teaser`（Coming Soon） | 开关存不住，前台没有预告锁定，编辑器出提示 |
| 9 | `09-deal.sql` | 五个 `sale_*` 文本列（限时秒杀） | 秒杀字段整体失效（秒杀角标/专区/倒计时都不出现），编辑器出提示 |
| 10 | `10-acc.sql` | `products.has_acc` / `acc_id`（ACC 佣金） | 开关存不住，前台不出 `ACC` 身份行，编辑器出提示 |
| 11 | `11-sub-badge-deal-priority.sql` | `sub_tag` / `sub_badge_color` / `deal_priority` | 副角标与专区置顶存不进去，编辑器/批量弹窗出提示（主角标、秒杀、分类不受影响） |
| 12 | `12-settings.sql` | `settings` 表（秒杀专区 Tab 的展示名） | 后台改名存不进去并提示；前台一直用默认名 `Limited Deals` |

### 四张表 + 一个视图

| 表 / 视图 | 存什么 | 匿名能读吗 |
|---|---|---|
| `products` | 商品行，一商品一行 | ✅ 能（红人要浏览） |
| `categories` | 栏目清单 + 排序 | ✅ 能 |
| `settings` | 站点级配置（key/value），目前只有秒杀 Tab 的展示名 | ✅ 能（红人要看到那个名字） |
| `asins` | 货号 → 变体 → ASIN | ❌ **不能**，只有 `admin_users` 里的人能读 |
| `product_links`（视图） | 每个商品一个 ASIN + 哪些组合有货号 | ✅ 能，但只此一个 ASIN，见下 |

`products.specs` 和 `products.variant_images` 是 `json`（**不是 `jsonb`**），下面单独讲为什么。

`sort_order` 决定顺序，**不放进商品对象**。前端拿到的商品数组是按 `sort_order` 排好的，商品对象本身没有这个字段 —— 否则选款码和导出 JSON 里会多出一个跟业务无关的数字。

### RLS 三条规则

```sql
-- 读：红人免登录
create policy products_read on public.products for select using (true);

-- 写：必须是白名单里的管理员
create policy products_write on public.products for all
  to authenticated
  using (public.is_admin()) with check (public.is_admin());

-- ASIN 连读都要白名单
create policy asins_read on public.asins for select using (public.is_admin());
```

`is_admin()` 查的是 `public.admin_users` 白名单，**不是** `auth.role() = 'authenticated'`。原因：Supabase 默认允许自助注册，用「已登录」当管理员等于门没锁。

### Realtime 必须同时满足两个条件

这是最容易踩的坑，而且**失败时没有任何报错** —— 订阅建立了，就是收不到事件。

1. 表在 `supabase_realtime` publication 里
2. 订阅的那个角色对该表**有 SELECT 策略**

第 2 条常被漏掉。Supabase 的 Realtime 在推送前会按订阅者身份过一遍 RLS，没有 SELECT 策略就等于没有广播权限，静默丢弃。

本项目的对应关系：

| 表 | publication | anon SELECT | authenticated SELECT | 结果 |
|---|---|---|---|---|
| `products` | ✅ | ✅ | ✅ | 前后台都能实时刷新 |
| `categories` | ✅ | ✅ | ✅ | 同上 |
| `asins` | ✅ | ❌ | 仅白名单 | **只有登录后台的人收到** |

`asins` 是有意的：匿名不该知道 ASIN，所以匿名也收不到 ASIN 的变更。这是正确行为，不是 bug。

### 前台要跳亚马逊，但不能交出全部 ASIN（`product_links` 视图）

前台每张卡片要有 `https://www.amazon.com/dp/{ASIN}` 链接，可 `asins` 表匿名一行都读不到。折中办法是一个**只读视图**，只暴露「一个商品对应的那一个 ASIN」：

```sql
create or replace view public.product_links
with (security_invoker = off) as
select product_id, asin, linked_variants from ...;
```

- `asin` = 该商品**第一个**变体的 ASIN（`json_each_text ... with ordinality ... limit 1`），正是链接里本来就会露出来的那一个
- `linked_variants` = `{"Black|M": true, …}`，只说明"这个组合有货号"，**不含任何 ASIN 值**。颜色名本来就在 `products.specs` 里公开
- `security_invoker = off` 是必须的：让视图以定义者身份读底表，匿名才拿得到；`asins` 本身的 RLS 不动，4509 行照旧只有白名单能读
- 授予：`grant select on public.product_links to anon, authenticated;`

建表语句在 `supabase/04-product-links.sql`。**没跑这个脚本时前台不报错** —— `linkStore` 静默失败，卡片上的链接位显示 `Listing not linked yet`。跑完刷新即可，不用重新部署（视图读的是实时数据，后台改了货号，前台链接立刻跟着变）。

> **踩过的坑：视图版本比代码旧，全部链接消失。**
>
> 视图一开始只有 `product_id, asin` 两列，`linked_variants` 是后来加的。而 PostgREST 对**不存在的列**不是返回空值，是整条请求 400（`42703`）。所以只要数据库里还是旧版视图，`select('product_id, asin, linked_variants')` 就整个失败 —— 连那个明明存在的 ASIN 一起丢掉，前台一个链接都不渲染，而数据库看起来完全正常。
>
> 现在 `linkStore` 用 **`select('*')`**，对两个版本的视图都成立：一次请求、网络面板里没有失败调用，靠返回的行里有没有 `linked_variants` 判断版本。旧视图下链接照常显示，只有「这个组合没上架」的提示会静默关掉（不知道 ≠ 没有，不能反过来吓用户）。
>
> 判断当前是哪个版本：`curl "$URL/rest/v1/product_links?select=*&limit=1" -H "apikey: $KEY"`，看返回里有没有 `linked_variants`。没有就重跑一次 `04-product-links.sql`（`create or replace view` 可以往后加列）。

配套的一条硬规则：**`src/` 下任何文件都不许 import `data/asins.js`**。动态 `import()` 也不行 —— Vite 只是把它拆成另一个 chunk，`dist/assets/asins-xxxx.js` 照样一个 URL 就能下走。`asinStore` 现在完全靠 Supabase；`data/asins.js` 只留给 `npm run push` 和 `scripts/decode.mjs` 这类 Node 侧工具用。

同理，`public/` 下**不能放任何含全量数据的东西**：`public/*` 会原样进 `dist/`，谁都能 curl。旧的 `public/import.js`（localStorage 时代生成的 208 kB 控制台脚本）就踩了这个坑，现已改生成到 `scripts/out/import.js`。

### 为什么 `specs` 用 `json` 而不是 `jsonb`

还有一点：**socket 上带的是登录时的 JWT**。所以 `auth.js` 里每次登录成功都要重新 `startRealtime()` —— 用旧 token 建好的通道不会因为登录而升级权限。

前端收到事件后的动作是**整表重取**（去抖 180 ms），不是按 payload 打补丁。原因：一次改动可能同时挪动 `sort_order`，批量操作会连发几十个事件，打补丁容易算出中间态。180 ms 足够把一次批量操作合并成一次请求。

### 为什么 `specs` 用 `json` 而不是 `jsonb`

**这是全项目风险最高的一行建表语句。**

v4 选款码按**位置**编码选项值，位置对齐的是 `Object.keys(product.specs)` 的顺序：

```
specs = { Colour: [...], Size: [...] }   →  码里第 1 位是颜色，第 2 位是尺码
```

`json` 保留键的原始顺序；`jsonb` 会**按 key 长度重排**，于是 `{Colour, Size}` 读回来变成 `{Size, Colour}` —— 颜色和尺码在解码时**静默对调**。没有报错，没有崩溃，只是所有人的订单颜色尺码全错。

所以：

- 列类型必须是 `json`
- `01-schema.sql` 里留了长注释说明这件事
- `scripts/push-supabase.mjs` 导入后会**重新读一行回来断言 key 顺序**，不对就报错并给出修复 SQL
- `npm test` 里的 `test-mapping` 专门盯这一条

### id 由数据库发

老版本用「当前最大值 + 1」在客户端算 id，两个人同时新增就会撞。现在是 `products_id_seq` + `next_product_id()`：

```sql
create sequence if not exists public.products_id_seq;
-- createProduct 不传 id，让序列分配
```

序列只往前走，所以**删掉的 id 永远不会被重新发出去** —— 这是选款码按 id 存的前提。删了 p047，以后不会再有第二个 p047。

### 导入

```bash
npm run push -- --dry-run   # 先看要写什么
npm run push                # 真写
npm run push -- --fresh     # 先清空再写（危险）
npm run push -- --only=products
```

脚本优先用 `SUPABASE_ADMIN_EMAIL` 登录后写入，这样顺便验证了 RLS 是对的（能写说明策略通）。也支持 service_role key，但那是绕过 RLS 的，只在可信机器上用。

导入结束会做四项校验：商品数、分类数、ASIN 数、`specs` key 顺序，另外**用匿名 client 复查一遍** —— 商品必须读得到，ASIN 必须读不到。任何一项不对就非零退出。

### 附：以后想换短码 → Cloudflare Workers + KV

选款码现在仍是自包含的（见第八节），这是刻意的：红人手机没网也能生成，运营粘贴就能查，不依赖任何服务在线。如果以后想要 6 位短码和「谁选了什么」的统计，再加一层 KV：

```js
export default {
  async fetch(request, env) {
    const url = new URL(request.url)
    const cors = {
      'Access-Control-Allow-Origin': '*',
      'Access-Control-Allow-Methods': 'GET,POST,OPTIONS',
      'Access-Control-Allow-Headers': 'Content-Type',
    }
    if (request.method === 'OPTIONS') return new Response(null, { headers: cors })

    if (url.pathname === '/api/save' && request.method === 'POST') {
      const body = await request.json()
      const code = Math.random().toString(36).slice(2, 8).toUpperCase()
      await env.SELECTIONS.put(`sel:${code}`, JSON.stringify(body))
      return Response.json({ code: `aoysky-${code}` }, { headers: cors })
    }

    if (url.pathname === '/api/get') {
      const code = url.searchParams.get('code')?.replace('aoysky-', '')
      const data = await env.SELECTIONS.get(`sel:${code}`)
      return Response.json(data ? JSON.parse(data) : null, { headers: cors })
    }

    return new Response('Not found', { status: 404, headers: cors })
  },
}
```

```toml
# wrangler.toml
name = "mako-selection-api"
main = "worker.js"
compatibility_date = "2024-01-01"

[[kv_namespaces]]
binding = "SELECTIONS"
id = "你的KV命名空间ID"
```

前端只需把 `utils/code.js` 的 `generateCode` 改成 `POST /api/save`、`decodeCode` 改成 `GET /api/get?code=xxx`，组件层完全不用动。

> ⚠️ 注意：这么做之后选款码就**不再自包含**了，断网或服务挂了就解不开。真要换，建议保留现有长码作为兜底（短码查不到时回退本地解码）。

## 十二、已知限制

| 限制 | 说明 | 后续方向 |
|---|---|---|
| 后台登录绕不过，但界面挡不住 | 数据是真保护的（RLS），但 `#` 路由让 Cloudflare Access 看不到 `/admin`；能登录的人仍能改数据 | 拆独立子域 + Access，见第十四节 |
| 依赖 Supabase 在线 | 断网时前台是空目录，不再有本地兜底 | 可加只读缓存（Cache API），代价是多一层一致性要维护 |
| 匿名可读全部商品 | 商品名/颜色/尺码本来就是公开信息，只有 ASIN 是白名单 | 要连商品也保护，得让前台走带鉴权的 API |
| 每款上限 35 件 | 数量用 1 个 base36 字符 | 改 2 字符即可扩到 1295 |
| 码还是偏长 | 2 款约 65 字符，4 款约 110，6 款约 150 | 要 6 位短码得上 KV，见第十一节附录 |
| 已删商品的规格没标签 | 类型名不进码，只剩 `Option 1` / `Option 2` | 值仍在，够对单；要标签得把类型名写回码里 |
| 变体组合是笛卡尔积 | 前台颜色 × 尺寸可选出表格没有的搭配 | 会显示 `No matching ASIN`；要禁选得按颜色拆商品 |
| 图片只能用 URL | 没有上传入口，图片得先传到图床 / CDN | 有意为之，见第六节 |
| 长裤在内衣旁边显得小 | 正方形画框 + `contain`，0.43 的源图在 260px 画框里只占 112px 宽 | 不是 CSS 能解决的：在源图上统一裁成正方形、商品占 80%，或者接受 `cover` 的裁切 |
| 分页不记忆 | 刷新或换分类回到第一批 24 个 | 有搜索框之后够用了；真要记住得写进 URL 或 localStorage |
| 搜索只认货号和名称 | 搜不了颜色、分类、ASIN（前台拿不到 ASIN 表） | 要搜 ASIN 得把 `product_links` 也下发到前台 |
| 一款一套规格 | 同款不同色算同一行 | 需要拆行时按颜色拆成独立商品 |
| 同款多色要选两次 | 同一款每个颜色/尺码组合是一行，选 3 个组合就是 3 行 | 有意为之：红人需要分别指定每个组合的数量 |
| 亚马逊链接依赖视图 | 没跑 `04-product-links.sql` 时链接位显示 `Listing not linked yet` | 跑一次即可，之后跟随数据库实时变化 |
| 断货要手动标 | 没有库存数量，也没有「卖完自动断货」，全靠编辑器里勾 | 有意为之：这里没有下单数据可对；要自动得接 ERP 库存 |
| 断货不拦旧码 | 已发出的码解码后仍显示原颜色/尺码，后台不会提示「这行现在断货了」 | 断货是当下的库存状态，不是历史事实；要提示得查码时联表看 `sold_out_variants` |
| 无选款统计 | 选款码不进数据库，查过就没了 | 要统计得把码落库，见第十一节附录 |
| ASIN 不参与下单 | 只用于后台展示和搜索 | 接 ERP 时按 ASIN 拆单 |
| 分类没有层级 | 只有一层平铺，没有父子分类 | 栏目多了可以改成两级 |
| 分类删除不可撤销 | 删掉的分类要重新加，商品会落到 `Uncategorised` | 删除前有行内确认，误删概率低 |
| 商品删除不可撤销 | 云端没有软删除，删了就是删了 | 要留痕得加 `deleted_at` 列 |
| 登录会话只在当前标签页 | `sessionStorage`，关标签页就退出 | 共用电脑时这是优点；嫌麻烦改成 `localStorage` |

已不再有的限制：~~商品上限 32 个~~（v3 起不再用位掩码）、~~商品顺序敏感~~（v3 起存 id）、~~ASIN 只能按货号给一堆~~（现在按颜色+尺寸给一个）、~~码里塞名称快照太长~~（v4 去掉了）、~~上传图撑爆 localStorage~~（已改为只收 URL）、~~所有颜色共用一张图~~（现在每个颜色可以有自己的图）、~~分类写死在代码里~~（现在后台可增删改名）、~~下架只能删商品~~（现在有隐藏开关和批量操作）、~~后台裸奔谁都能进~~（现在走 Supabase Auth + 白名单）、~~改完要手动导出再发文件给同事~~（现在多人实时同步）、~~两个人同时新增会撞 id~~（现在由数据库序列发号）、~~密码就在打包的 JS 里~~（现在没有任何前端口令）、~~同款只能选一次~~（现在按「商品 + 颜色 + 尺码」加购，v5 码支持同款多行）、~~列表页卡片图会跟着颜色跳~~（现在卡片永远用主图）、~~全量 ASIN 躺在 JS 包里~~（现在 `dist/` 里一个 ASIN 都没有）、~~139 个商品一屏平铺到底~~（现在分批加载 + 货号/名称搜索）、~~清空购物袋只能一个个删~~（现在有 Clear all）、~~一个尺码卖完就得下架整个款~~（现在能按颜色+尺码标断货）。

## 十四、后台访问门禁

`/#/admin` 开头的所有路径都要先登录。**是 Supabase Auth 的邮箱 + 密码，不是前端口令。**

### 从选款页怎么进后台

前台页面上有两个入口，都是给运营用的，红人基本不会碰到：

| 方式 | 位置 | 说明 |
|---|---|---|
| 页脚 `Admin Login` | 滚动到商品网格底部，声明那行下面 | 11px、45% 浅灰，hover 才稍微变深 |
| **直接键盘输入 `admin`** | 选款页任意位置 | 不用找链接；输入框里打字不会触发 |

键盘那条的实现是「1.2 秒内连续敲出 a-d-m-i-n」。它只在选款页生效，并且在 `input` / `textarea` / `select` / contenteditable 里打字时完全不响应，带 Ctrl / ⌘ / Alt 的组合键也一律忽略 —— 所以红人搜商品、填选款码都不会误触。

为什么要有键盘那条：页脚链接是**故意做得很淡**的，如果只留链接，新同事得先被告知"滚到底部找一行灰字"。有了快捷键，口头交代一句"在选款页敲 admin"就够了。

进去之后仍然要登录（见下），所以这个入口暴露出来也不等于泄露数据。

### 怎么用

1. 打开 `/#/admin` → 全屏 **Access Required**
2. 输管理员邮箱 + 密码 → 进入后台
3. 当前标签页内刷新、切页签都不用重登
4. 右上角 **Log out** 立刻回锁

### 账号从哪来

两件事缺一不可：

1. **Supabase → Authentication → Users** 里有一个已确认的用户
2. **`public.admin_users` 表里有这个 user 的 id**

```sql
insert into public.admin_users (user_id, email)
select id, email from auth.users where email = 'ops@yourbrand.com';
```

只做第 1 步、忘了第 2 步，症状是：密码正确、登录成功，但门禁一直转圈然后提示没有后台权限。这是白名单在起作用，不是 bug。

加人就是重复上面这一步。撤权：

```sql
delete from public.admin_users where email = 'someone@yourbrand.com';
```

撤权之后对方手里的 token 还没过期，但下一次写数据会被 RLS 拒掉 —— 写入才是真正的边界。

### 通行证存在哪

| | |
|---|---|
| 存储位置 | `sessionStorage`（Supabase 默认用 localStorage，这里特意改了） |
| 存的值 | Supabase 的 access token + refresh token |
| **不存什么** | 不存密码。密码只在登录那一刻发给 Supabase，前端不落地 |
| 有效期 | 当前标签页。关掉标签页即失效，新开标签要重登 |
| 为什么不用 localStorage | 共用电脑时不会留下永久后门 |

改成 `sessionStorage` 是在 `src/lib/supabase.js` 里配的：

```js
const tabStorage = {
  getItem: (key) => sessionStorage.getItem(key),
  setItem: (key, value) => sessionStorage.setItem(key, value),
  removeItem: (key) => sessionStorage.removeItem(key),
}
```

### 为什么不会「闪现」

门禁不是盖在后台页面上的一层遮罩，而是**锁着的时候根本不渲染后台组件**：

```jsx
export function AdminGate({ children }) {
  if (status === 'loading') return <GateShell />        // 骨架，什么都不露
  if (!isAdmin) return <AccessGate />                   // 后台组件根本没被 mount
  return children
}
```

所以锁屏状态下 DOM 里没有 `Product library`、没有页签、没有查询框 —— 不是「藏起来了」，是**不存在**。遮罩方案在慢网络或 React 首帧时会有半透明闪现，这里不会。

覆盖范围是父路由，`/admin` 下面加任何新页签都自动受保护；再配一个 `path="*"` 兜底，连 `/admin/随便写` 也落在门禁后面（显示 Page not found，而不是白屏）。

### 这个门禁有多安全

比前端口令强一个量级，因为**拦人的是数据库，不是界面**：

| 攻击方式 | 结果 |
|---|---|
| F12 搜密码 | 搜不到，bundle 里没有任何口令 |
| 改 `sessionStorage` 伪造 token | 签名验不过，PostgREST 直接 401 |
| 用 anon key 直接 `POST /rest/v1/products` | RLS 拒掉，`is_admin()` 返回 false |
| 拿 anon key 读 `asins` | 返回空数组（策略是 `is_admin()`） |
| 猜 `/#/admin` 地址 | 只能看到登录框 |

剩下能突破的只有：**拿到管理员密码**，或者**拿到 service_role key**（那个 key 只在脚本里用，永远不进前端）。

### 还有一层：Cloudflare Access

**先记住这个前提（很多人在这里踩坑）：Cloudflare 看不到 `#` 后面的东西。**

浏览器不会把 hash 发给服务器。HashRouter 下 `/#/admin` 和 `/#/` 对 Cloudflare 是**完全同一个请求** `GET /`。所以：

> ❌ Cloudflare Access 无法只保护 `/#/admin` —— 它没有这个信息。
> ✅ 必须先把后台放到**真实路径**或**独立域名**上，Access 才有东西可保护。

不过和以前不一样了：**现在就算不做这一层，数据也是安全的**（RLS 兜底）。Access 在这里的价值变成了「连登录框都不给外人看」，属于锦上添花，不是必需。

按投入从低到高，三条路：

#### 方案 A：后台拆独立子域 + Cloudflare Access

最彻底，代码几乎不用改。

1. 同一个仓库再建一个 Pages 项目（比如 `mako-admin`），构建命令不变
2. 绑定自定义域 `admin.your-domain.com`
3. Cloudflare Dashboard → **Zero Trust** → Access → Applications → **Add an application → Self-hosted**
4. Application domain 填 `admin.your-domain.com`（路径留空 = 整个子域）
5. Policy：`Allow` → `Emails` 填团队邮箱；或者选 `One-time PIN`（什么都不用配，收邮件验证码）
6. 免费版 50 个用户，够用

效果：**边缘就拦住**。没登录的人拿到的是 Cloudflare 的登录页，连你的 HTML 都下载不到。

唯一要补的一步：主域那份部署**不应该包含后台代码**，否则别人还是能从 `主域/#/admin` 摸到登录框（虽然登不进去）。做法是加一个构建开关：

```js
// App.jsx 里按环境变量决定是否挂载 admin 路由
const ADMIN_ENABLED = import.meta.env.VITE_ADMIN === '1'
```

```bash
VITE_ADMIN=1 npm run build     # 后台子域用这份
npm run build                  # 主域用这份，不含后台路由
```

这样主域的 `/#/admin` 直接是 404，后台只存在于被 Access 保护的那个域名上。

#### 方案 B：Pages Functions 中间件（不想拆项目）

需要先把后台从 hash 路由改成真实路径 `/admin`（`BrowserRouter` + `public/_redirects` 兜底），然后加一个中间件文件：

```js
// functions/admin/_middleware.js
export async function onRequest({ request, next }) {
  const auth = request.headers.get('Authorization') || ''
  if (auth.startsWith('Basic ')) {
    const [, pass] = atob(auth.slice(6)).split(':')
    if (pass === process.env.ADMIN_PASS) return next()   // 存在 Pages 环境变量里
  }
  return new Response('Unauthorised', {
    status: 401,
    headers: { 'WWW-Authenticate': 'Basic realm="Aoysky admin", charset="UTF-8"' },
  })
}
```

零依赖、几十行、跑在 Cloudflare 边缘，口令不进前端 bundle。缺点是 Basic Auth 每次都发密码，且没有登出按钮 —— 想更正规还是用 Access 包住这个路径。

#### 方案 C：什么都不做

完全可以。数据层已经是真保护：匿名读不到 ASIN、匿名写不进任何表。Access 挡的是「外人看见有个后台」，不是「外人改你的数据」。

顺手能做的两件小事：

```
# public/_headers
/*
  X-Robots-Tag: noindex, nofollow
  X-Frame-Options: DENY
```

- `noindex` 防止后台页面被搜索引擎收录
- 别把 `/#/admin` 链接发在公开渠道

### 现在的组合

```
前台（公开，anon key）
  └─ /#/            ← 红人随便用，只读

后台（Supabase Auth + admin_users 白名单）
  ├─ 第一道：登录墙（已实现，密码正确才进得去）
  ├─ 第二道：RLS（真正的边界，anon 一个字节都写不进）
  └─ 可选第三道：Cloudflare Access（拆子域后可用，边缘拦截）
```

三道里**只有第二道是硬的**。第一道防误入，第三道防围观；即使前两道都被绕过，RLS 仍然拦着。

## 十五、性能：首屏那 10 秒是怎么没的

红人反馈"手机上打开要 10-15 秒"。查下来不是一个原因，是四层叠加。下面的数字全部来自
`scripts/perf-check.mjs`：Slow 4G（400 ms RTT / 400 kbit/s）+ CPU 4× 降速 + 390×844 视口，
改前改后同一台机器、同一套参数。

| 指标 | 改前 | 改前（Google 字体 +6s） | 改后 | 改后（字体 +6s） |
|---|---|---|---|---|
| 首屏有内容（FCP） | 5.42 s | **7.56 s** | **1.79 s** | 1.78 s |
| 第一张商品卡 | 7.91 s | **10.07 s** | 6.55 s | 6.52 s |
| 第一张图片可见 | 10.98 s | **13.31 s** | 9.08 s | 9.07 s |
| 单次访问字节 | 340 kB | 340 kB | **267 kB** | 267 kB |
| 请求数 | 23 | 24 | **19** | 20 |
| 复访（同一标签页） | — | — | **1.18 s / 1.28 s** | — |

### 15.1 罪魁祸首：`<head>` 里的 Google Fonts

原来的 `<link href="https://fonts.googleapis.com/css2?...">` 是**渲染阻塞**的。跨域样式表
不返回，浏览器一帧都不画 —— 表现就是纯白屏，而且时长完全取决于 Google 的心情。
把这条请求人为拖 6 秒，FCP 从 5.42 s 涨到 7.56 s，**涨幅正好是那条 link**。

删掉它，字体退回系统栈（`ui-sans-serif` / PingFang SC / Segoe UI / Roboto）。
零请求、零字节，手机上反而更快。改后即使把字体请求拖 6 秒，FCP 一动不动（1.79 → 1.78 s）——
因为已经没有任何人去找 Google 了。

### 15.2 静态首屏：JavaScript 还没跑起来的那 4 秒

`index.html` 里有一段**内联**的骨架（约 1.5 kB HTML+CSS，无图片、无字体、无请求）。
React 一挂载就把它替换掉，然后由 `ProductGrid` 里的 React 骨架接棒。

为什么需要两份：bundle 在 4× CPU 下要 **4.1 秒**才执行完，在那之前 React 画不出任何东西
—— 截图实测，2.6 秒时页面是一个空的米色矩形。静态骨架在 HTML 解析时（~0.6 s）就出现，
这是 FCP 从 5.4 s 掉到 1.8 s 的第二个原因。

两份骨架的分工写在两边注释里：静态那份不能 import 任何东西，React 那份负责真实卡片的几何；
**改网格布局时两边都要改**。

### 15.3 图片：741 px 的图塞进 169 px 的格子

商品图来自亚马逊 CDN，URL 里就带着尺寸（`._AC_SY741_`）。卡片在手机上只有 169 CSS px 宽，
2× 屏也就 338 设备像素 —— 一直在下载 3 倍的像素。实测同一张图：

| 请求 | 字节 |
|---|---|
| `_AC_SY741_`（原样） | 17.6 kB |
| `_AC_SY640_` | 10.3 kB |
| `_AC_SY320_` | **5.8 kB** |

`utils/image.js` 只改这一段 token，配 `srcSet 320w/640w + sizes`（`sizes` 与网格列宽严格对应，
写大了浏览器会偷偷下大的）。**不能改的 URL（占位图、非亚马逊域名）原样返回，也不生成 srcset** ——
否则等于告诉浏览器"这个文件是 320px 宽"，那是撒谎。

一个真坑：`ProductImage` 的兜底链在换 `src` 时必须**同时清掉 srcSet**，因为 srcset 优先级高于 src，
否则图挂了会一直挂，占位图永远不出现。

### 15.4 复访：sessionStorage 里放一份目录

`productStore` 在**模块导入时**读 `sessionStorage` 里的上一次目录（12 小时 TTL），
第一帧就有数据；网络请求照发，回来后原地替换。用 sessionStorage 不用 localStorage：
关掉标签页就没了，陈旧数据不会活过这次会话。

代价写在代码注释里：刷新落地前的那几百毫秒里，上次之后被删掉的商品还能看见。
`reconcileLines` 随后会把购物车里指向它的行清掉，和线上删除走同一条路径。

效果就是表里最后一行：复访 **1.18 s 首屏 / 1.28 s 出卡片**（改前同样要 7.9 s）。第一次访问
没有缓存，只能等网络，这是唯一没法省的部分。

### 15.5 顺手拆掉的三件事

1. **后台代码不再进红人的包**。原来 282 kB（79 kB gzip）的入口里塞着 ProductsPage（1,600 行）、
   商品编辑器和 dnd-kit。改成 `React.lazy` 后入口 **139 kB（38 kB gzip）**，
   后台变成按需加载的 130 kB 分包 —— 慢速网络上省了约 0.8 秒，而红人永远不会打开那一屏。
2. **匿名不再请求 `asins`**。那张表只对 `authenticated + is_admin()` 开放，红人拉它必然返回空数组，
   纯粹多一个跨洋往返。现在只有存在会话时才拉，管理员登录后再补一次。
3. **Realtime 延后到首屏之后**。一个 websocket + 三张表的订阅对首屏毫无贡献，
   改成 `requestIdleCallback`（兜底 2.5 s）。
4. **渲染范围收紧**：`Header` / `CategoryNav` / `BottomBar` / `ProductCard` 全部 memo，
   搜索用 `useDeferredValue` —— 打字时输入框先响应，列表再跟上，不再每敲一个字就同步重排 24 张卡片。
   `ProductCard` 的 memo 需要自定义比较函数（父组件每次渲染都会重建 `lines` 数组），
   否则浅比较永远判定"变了"，memo 反而更慢。

### 15.6 怎么复测

```bash
npm run build
npm run preview -- --port 4173          # 静态产物，和生产同一份
node scripts/perf-check.mjs http://localhost:4173 --warm
node scripts/perf-check.mjs http://localhost:4173 --delay-fonts   # 模拟 Google 字体不可达
```

`--warm` 会在同一个标签页里测第二次，那才是复访的真实体感。
